# CQB-HTML

단일 파일 CQB(근접전투) 전술 시뮬레이터. **모바일 가로화면**을 기준으로 개발한다.

개발 소스는 시스템별 JS·CSS·HTML 템플릿으로 관리하고 배포할 때 HTML 한 파일로 합친다. 원본을 보존하면서 Three.js·Rapier 기반 **M4A1·AK-74M 3D 훈련장**을 별도 앱으로 추가했다. [훈련장 실행·구조](apps/training/README.md), [개발 안내](docs/development-guide.md), [3D 전환 설계](docs/3d-extraction-architecture.md), [레이드 개발 계획](docs/raid-prototype-plan.md)을 참조한다. 원본 방호 저지·내구도·인체 저항도 3D 메시 교차에 연결했다. [방호·인체 v10 검증](docs/training-protection-verification.md)을 따른다. H01은 고정 A 자세의 피격·방호·의료 확인용 표적이다. 인체 출구 속도/침착 에너지와 원본 의료 상처·출혈·부위 기능·전신 상태를 연결했다. 기존 캐릭터의 안쪽 군복과 장비 연결도 수리했다. [M 검증](docs/training-m-verification.md), [시각 스킨 수리](docs/training-skin-verification.md). v32에서 의료에 따른 NPC 쓰러짐·첫 적 AI·플레이어 피격을 추가했다. 치료·원본2D AI 판단 이식·익스트랙션 레이드는 후속이다.

## 실행

원본은 기존처럼 `CQB_Tactical.html`을 브라우저로 열면 된다. 가로화면 전용이며 세로화면에서는 회전 안내가 뜬다.

소스 개발과 배포 파일 생성에는 Node.js 22 이상을 사용한다. 기존 2D 빌드는 Node 내장 모듈만 사용한다. 3D 훈련장과 전체 테스트는 `npm ci`로 의존성을 설치한다.

```sh
npm ci
npm run dev:training      # http://127.0.0.1:5174
npm run build:training    # 모델·WASM까지 내장한 dist/CQB_Training.html
npm run test:training
npm run test:training:browser  # Playwright Chromium 설치 필요
```

훈련장은 이동·앉기·ADS·재장전, 총이 먼저 움직이고 카메라가 뒤따르는 바디캠 방식, ADS 가늠쇠 선행·보행 중 흔들림·정지 후 조준기 정렬 회복, 총구 방향 사격·고정 표적 적중, 섬광·탄피·피격 효과를 제공한다. 비조준 총기의 기본값은 크기 115%·높이 −1cm이며, 오른쪽으로 1.5cm 옮겼다. 보행 상하 움직임은 기존보다 25% 줄였다. 왼쪽 패드로 이동하고 오른쪽 사격 버튼을 누른 채 드래그해 조준과 사격을 함께 한다. 설정에서 일반·ADS 감도, 총기 크기·높이·움직임 강도, 카메라 프리셋·추종을 조절할 수 있다. 가로→세로 회전과 앱 전환은 훈련을 멈추고 입력을 해제한다.

기존 2D 실행·빌드는 다음과 같다.

```sh
npm run dev              # http://127.0.0.1:5173, 소스 수정 후 브라우저 새로고침
npm run build            # dist/CQB_Tactical.html 생성
npm run verify:baseline  # 이번 소스 분리의 원본 바이트 동일성 확인
npm test                 # 2D 빌드·개발 서버 + 3D 계산·물리 검증 (npm ci 필요)
```

생성 파일은 JS·CSS를 내장하므로 별도 서버나 외부 파일 없이 전달할 수 있다. 개발 수정은 `src/`에서 하고 보존 원본과 `dist/`를 직접 수정하지 않는다. 현재 JS 파일들은 원본 순서대로 **하나의 classic script**로 합쳐진다. 독립 ES module·DOM 없는 계산 코어로 전환하는 것은 다음 단계다.

브라우저 회귀 검증은 `npm ci`, `npx playwright install chromium` 후 `npm run test:browser`로 실행한다. 원본과 생성본의 기존 272개 사례를 대조하며, 기존 C2 실패 1개와 validator 경고 1개를 명시적으로 기록했다. 새 실패는 허용하지 않는다. 자세한 결과와 모바일 검증 범위는 [개발 안내](docs/development-guide.md#현재-검증-결과)에 있다.

## AI 공간 인지 (SpatialPerception)

AI의 지형 기억 계통. `reference/tactical_prototype_0.8.0.html`에서 이식했다.

두 시야는 역할이 다르며 겹치지 않는다.

| | 담당 | 이번 교체 |
|---|---|---|
| `checkVisibility` | 저 유닛이 지금 보이는가 (적 탐지·먼지·바이저·자세) | 건드리지 않음 |
| `SpatialPerception` | 이 방이 어떻게 생겼다고 믿는가 (지형 기억) | 교체 대상 |

핵심 차이는 **AI가 틀릴 수 있게 됐다**는 것이다.

- 기존 `knownCovers`는 정답 객체 id를 들고 있어 낡을 뿐 결코 틀리지 않았다.
- 새 기억(`aiMemory.spatial.surfaces`)은 관측으로 재구성한 가설이다. 한 직선 위
  관측을 최대 6.5m 간극까지 이어 붙이므로, **출입구를 벽으로 착각**할 수 있다.
- 기억한 벽을 뚫고 보이면 `reconcileMemory`가 그 기억을 쪼개거나 지운다(반증).
- 두께는 양면을 봐야 추론되고, 그때만 관통저항 추정이 올라간다.
- **재질도 틀릴 수 있다** (아래).

### 재질 인지

벽이 거기 있다는 건 멀리서도 알지만, 콘크리트인지 강철인지는 가까이서 정면으로
봐야 안다. 그래서 재질 증거(`materialEvidence`)에는 기하 신뢰도와 **다른** 거리·입사각
감쇠가 걸린다 (`MAT_DIST_NEAR` 6m ~ `MAT_DIST_FAR` 22m).

증거가 쌓이며 3단계로 확정된다. 단계가 바뀔 때만 갱신하므로 값이 흔들리지 않는다.

| `materialKnown` | 믿는 재질 | 오버레이 표기 |
|---|---|---|
| `unknown` | 가장 보수적으로 `concrete` 단정 | `concrete??` |
| `class` | 등급 대표값 (soft→`wood` / medium→`thin_metal` / hard→`concrete`) | `wood?` |
| `exact` | 실제 재질 | `wood` |

등급 경계는 `MATERIAL_ARMOR_PER_M` 표의 실제 간극에서 나온다(별도 표 없음).
**중간 단계가 쓸모 있는 오류가 사는 곳**이다 — 강철 벽이 콘크리트로 읽혀 AI가
방호력을 과소평가하고, 나중에 그 대가를 치른다.

측정치 (CQB 맵, 2회 평균): 재질 오인율 10초 8.5% → 30초 6.6%, 정확 재질 인지율
10초 47% → 30초 75%. 교전이 벌어지는 10~30초 구간에 오인이 살아 있다.

> `believedMaterial`은 진단·오버레이만 읽는다. **AI 판단 경로는 아직 연결되지
> 않았다** — 벽 관통 판단(`findFirstBarrierBetween`)은 여전히 정답을 읽는다.

### 소스 스위치

```js
const USE_SPATIAL_PERCEPTION_AS_SOURCE = true;   // 파일 상수
GAME.spatialPerceptionOn = false;                // 런타임 A/B (재로딩 불필요)
```

`true`면 아래 정답 기반 기록기가 전부 조기 반환하고, `mirrorToLegacyMemory`가 믿음에서
같은 자료구조를 역산해 채운다. 기존 소비자는 하나도 고치지 않았다 —
항목의 `believed: true`로 구분한다.

| 게이트되는 기록기 | 믿음에서 파생되는 것 |
|---|---|
| `recordCover` / `recordWall` | `knownCovers` / `knownWalls` |
| `recordSurfaceObservation` | `observedSurfaces` ← **정본 엄폐 경로가 읽는다** |
| `recordOpenSector` | `openSectors` |
| `tickMemoryValidation` | (반증은 `reconcileMemory`가 담당) |

`observedSurfaces`가 핵심이다. `findBestObservedCover`가 이걸 읽고,
`_findBestCoverImpl`은 그게 무엇이든 반환하면 즉시 반환한다(`knownCovers`는 fallback).
그래서 여기가 믿음이 실제로 엄폐 판단을 좌우하는 지점이다.

C1 슬롯 계층은 정답 객체가 없어도 동작하도록 **믿는 몸통**(`believedBody` — 면에서
법선 반대쪽으로 추정 두께, 미상이면 기본 깊이만큼 뻗은 사각형)을 받는다.
"이 엄폐물이 첫 차폐물인가" 검사도 `MAP_DATA`가 아니라 기억하는 면만 훑는다 —
**안 본 벽이 우연히 막아주는 것은 엄폐로 치지 않는다.**

> 하네스 스위트(`runAI0*`)는 샌드박스 안에서 스위치를 강제로 끈다. 그 스위트들은
> 레거시 정답 계약을 검증하므로 살아있는 스위치가 결과를 좌우하면 안 된다.

### 경로 — 기억한 지형 위에서 계획한다

`_findPathImpl`은 세계를 **술어 두 개**로만 본다. A* 본체는 그대로 두고 그 둘만
갈아끼웠다.

```js
findPath(sx, sy, gx, gy, unit)   // unit + 스위치 on → 믿음, 아니면 정답
```

**미지 공간은 뚫려 있다고 본다** (freespace assumption). 그래서 AI가 한 번도 본 적
없는 방으로 계획을 세우고 — 그게 탐색 행동의 정체다 — 대가로 실제 벽에 부딪힌다.

**그래서 접촉도 감각이다.** 부딪힌 지점에 짧은 표면을 심는다(evidence 0.55 —
`MEMORY_UNCERTAIN` 위, `MEMORY_CONFIRMED` 아래. 문 작업 중에 이 값이 문턱 아래라
아무 효과가 없었다는 걸 발견하고 고쳤다. 아래 문 절 참조).
남기지 않으면 같은 경로를 영원히 다시 계획한다. 나중에 제대로 보면
`absorbObservation`이 정식 관측으로 덮어쓰고, 끝내 못 보면 `pruneMemory`가 지운다.
연속 3회 막히면 그 목표를 잠시 접는다(폭주 방지).

> **경계선**: 바뀐 건 **계획 술어 둘뿐**이다. `pointInWalls` / `pathBlocked` 본체는
> 이동 충돌·`validateMoveTarget`·슬롯 물리검증에서 계속 정답을 쓴다.
> **물리가 정답이어야 AI가 틀렸다는 사실이 드러난다.**

측정치(CQB 25초, 스위치 on): 유닛 경로 3,593건 중 실패 0, 벽 접촉 14회 → 심은 표면
14개, 목표 쿨다운 1.3회, 갇힘 0, 움직인 유닛 12.3명(off는 8.3명).

## 문 (Door)

맵의 문간은 원래 벽에 뚫린 **빈 간극**이었다. 이제 실제 객체다 — 열리고, 닫히고,
문짝이 길을 막고, 약한 엄폐가 된다.

### 이산 상태가 AABB를 지킨다

엔진 전체가 축정렬 사각형 위에 있다(`rayBoxT` / `pointInWalls` /
`segmentIntersectsRect`). 문짝을 실제로 회전시키면 전부 깨진다. 그래서 상태를
둘로 두고, **두 상태 모두 축정렬 사각형**으로 만들었다.

| 상태 | 문짝 |
|---|---|
| `closed` | 간극을 메우는 얇은 판 (벽과 같은 방향) |
| `open` | 경첩 끝에서 벽과 **수직으로** 뻗은 얇은 판 |

스윙은 **렌더링만 각도를 보간한다**(`doorSwingProgress`). 충돌·시야·경로는 언제나
둘 중 하나의 사각형을 본다. 전환 중(`DOOR_OPEN_TIME` 0.9초)에는 **닫힘 사각형을
유지**하고, 지오메트리는 전환이 끝나는 순간 **한 번만** 바뀐다 —
그때만 `markTacticalGeometryChanged`로 그래프를 버린다.

`hinge`(간극의 어느 끝) × `swing`(벽의 어느 쪽으로 나가나)이 저작 속성이다.
열렸을 때 문짝이 **어느 방을 차지하는가**가 곧 안여닫이/밖여닫이의 전술적 의미다.

문은 `coverObjects`에 들어간다. 그래서 물리·시야·보행격자·엄폐 판정이
**아무것도 안 고쳐도** 문을 본다. 열린 문짝이 시야를 막고 이동을 막는 것 하나로
"문이 열리며 길을 방해"와 "약하지만 엄폐물"이 동시에 나온다.

### 계획은 통과, 물리는 차단

닫힌 문이 보행격자를 막으면 A*가 **문을 피해 돌아간다.** 그러면 아무도 문을 안 연다.

```
계획 지오메트리 = 정답 지오메트리 − 닫힌 문        (_planPointInWalls / _planPathBlocked)
물리 지오메트리 = 정답 지오메트리 그대로            (pointInWalls / pathBlocked)
```

닫힌 문 칸에는 통행 대신 **비용**(`DOOR_PLAN_COST`)이 붙는다 — 열린 길이 있으면
그쪽을 고른다. **열린 문짝은 계획에서도 그대로 장애물이다**(진짜로 거기 있으니까).

믿음 쪽도 같은 규칙이다. 표면 관측에 세 번째 출처 `door`가 생겨서,
`believedBodies(unit, { planning: true })`가 **기억하는 문을 뺀다.**
본 적 없는 문은 애초에 기억에 없어 freespace 가정으로 통행 가능하니 양쪽이 같은
답을 낸다. 정답 문 상태를 훔쳐보지 않는다.

### 개방 — `pendingDoor`

`setPendingMedic`/`tickPendingMedic`과 같은 모양이다. **아군·적 동일 규칙**이다.

- **수동**: 대원 선택 → 문 탭 → `doorApproachSpot`으로 이동 명령 → 사거리(`DOOR_REACH_M`)
  도달 시 개방
- **자동**: 이동 실행부가 진행 방향 `DOOR_LOOKAHEAD_PX` 앞의 닫힌 문을 보면 그 앞에
  서서 연다. 여는 동안 이동만 멈추고(`_doorHold`) 사격·시야는 그대로 돈다
- 접촉 대비: 벽 충돌 처리에서 막은 게 **닫힌 문뿐**이면 경로를 버리지 않고 개방으로 전환
- `DOOR_PENDING_TIMEOUT`(6초) 안에 못 닿으면 예약을 접는다 — 문 앞 정체를 만들지 않는다

여닫히는 문짝은 사람을 밀어낸다(`pushUnitsOutOfDoor`). 없으면 문을 연 본인이
문짝 안에 박힌다.

### 포탈은 문 상태와 무관하다

`_spatialFindWallGapDoorways`는 `M.walls`만 본다. 문은 coverObject라 **벽 간극은
그대로 간극**이고 포탈이 살아 있다. 문이 닫혔다고 문간이 사라지면 안 된다 —
"문이 거기 있고 지금 닫혀 있다"가 AI가 알아야 할 상태다.

### 왜 문간 네 곳 중 세 곳에만 문이 있나

CQB 맵 상단 복도벽에는 문간이 넷인데 문은 **셋**이다. 첫 문간(방 A)은 문틀만 있는
열린 통로로 남겼다.

실측하고 알았다 — 이 맵의 초기 교전은 그 문간을 지나는 **시선 하나**에 걸려 있다.
거기에 문을 달면, 열어 두어도 문짝이 대각선 시선을 가려서 양측이 서로를 아예 못 본다.
그러면 스위치 OFF(탐색 동기가 없는 레거시 AI)에서는 14명 전원이 `holdAngle`로 굳는다.

문 코드 탓이 아니다. **본편 baseline에 같은 자리·같은 크기의 평범한 엄폐물 4개를
넣어도 똑같이 굳는다** — 지오메트리를 그 문간에 놓은 것 자체가 원인이다.
그래서 코드가 아니라 맵 저작으로 풀었다.

### 곁가지 수정 — 접촉이 실제로 기억에 남게

`recordContact`가 심는 표면의 evidence가 **0.12**였다. 미러 문턱은
`MEMORY_UNCERTAIN = 0.30`이다. 즉 접촉 표면은 심자마자 문턱 아래라
`observedSurfaces`에 오르지 못했고, **계획을 한 번도 막지 못했다.**
"접촉도 감각이다"가 사실상 죽어 있었다.

0.55로 올렸다 — `MEMORY_UNCERTAIN` 위, `MEMORY_CONFIRMED`(0.62) 아래.
"부딪혔으니 뭔가 있는 건 알지만 보지는 못했다"가 정확히 이 구간이다.

실측(같은 지점에 접촉 하나 심고 직후 재질의):

| | 접촉 전 통행 가능 | 접촉 후 |
|---|---|---|
| 이전 (0.12) | true | **true** (믿음 몸체 16 → 16) |
| 지금 (0.55) | true | **false** (믿음 몸체 11 → 19) |

CQB 25초 기준 총 접촉 61.3 → 27.3회로 줄었고, **부딪힌 서로 다른 지점 수는
2.0 → 1.8로 그대로다.** 새로 부딪히는 건 freespace 가정이 하는 일이고,
줄어든 건 같은 자리를 다시 들이받는 헛수고다.

### 측정 (CQB 맵)

문 3개 앞에 각각 대원을 세워 반대편으로 보냈을 때: 닫힌 문 2개 모두 자동 개방,
지오메트리 무효화 **문 이벤트당 1회**, 지오메트리 안에 갇힌 유닛 0, 에러 0.
수동 탭 → 접근 → 개방도 성립하고, 열린 문을 다시 탭하면 아무 일도 안 한다.

25초 실행 지표:

| | 스위치 OFF | 스위치 ON |
|---|---|---|
| 경로 호출 / 실패율 | 1402 / 3.7% | 3630 / 0.0% |
| 벽 접촉 → 심은 표면 | 1.3 → 0 | 30.3 → 30.3 |
| 문 자동 개방 / 문 앞 대기 | 2 / **0** | 1 / **0** |
| 움직인 유닛 / 갇힘 | 9.3 / 0 | 11.7 / 0 |

> 이번 단계 범위 밖: 잠긴 문·돌파, AI가 전술적으로 문을 닫는 것.

## 믿음 방(Room) — 인식 · 명명 · 소음 기반 판단

AI가 지형을 방으로 본다. 방과 문턱은 **정답 그래프가 아니라 관측한 벽에서** 나온다.

### 지난 실패의 진짜 원인 — 개구부 ≠ 문턱

`USE_BELIEF_TOPOLOGY`가 꺼져 있던 이유를 측정으로 다시 찾았다. 조각난 믿음 때문이 아니었다.

`analyzeSector`의 "개구부"는 문턱이 아니라 **시선이 무한으로 빠져나가는 방향**이다.
문 너머 방의 벽을 한 번 보면 그 방향은 더 이상 escape하지 않는다 — 즉 **잘 알수록 0으로 수렴한다.**
실측: 제자리에서 360° 둘러보게 하니 전 유닛 링 닫힘 100% / 개구부 0개 / 문턱 후보 0개.
닫힌 건물에서 문턱 검출기로 쓸 수 없다. 개구부가 0이 되는 건 버그가 아니라 `sightClosed`,
"이 방은 다 봤다"는 정확한 신호다.

맞는 원시형은 **믿는 벽선 위의 간극**이다. 같은 직선·같은 법선을 가진 믿음 표면을 묶고,
그 사이 빈 구간이 문 너비(0.6~2.6 m)면 문턱.

### 경계는 세 종류다

```
벽       S.surfaces          믿는 표면 — 못 지나간다
문턱     S.thresholds        믿는 벽선 위의 간극 — 지나갈 수 있고, 너머는 다른 방
프론티어 S.sector.openings   아직 안 본 각도 — 벽인지 문인지 모른다
```

**같은 목록에 섞지 않는다.** 지난 시도가 정확히 프론티어를 문턱으로 착각한 것이었다.
상태기계(`detected → approached → crossed | observedBeyond`)와 동일성 판정
(`openingMatchScore`)만 공유하고 목록은 분리한다.

### 방을 다각형으로 만들지 않는다 (핵심)

믿음 방은 닫힌 도형이 아니다 — 경계에 구멍이 있는 게 정직한 상태다. 그래서
`getSpatialRegionAt(x,y)` 같은 **기하 질문을 믿음에 하지 않는다.** 필요한 질문은 둘뿐이고
둘 다 방 분할 없이 답이 나온다.

| 질문 | 답하는 방법 |
|---|---|
| 나는 어느 방인가 | 문턱을 넘기 전까지 같은 방. `crossesGate`가 이미 그 이벤트를 잡는다 |
| 저 소리는 어느 문으로 왔나 | 아는 문 중 **우회 거리가 가장 짧은 문** (나→문 + 문→소리) |

소음을 **직선 교차로 풀면 안 된다.** 소리는 벽을 관통해 오지 않고 문을 돌아 들어온다 —
다른 방 유닛 사이의 직선은 대개 문이 아니라 벽을 지난다(실측: 72쌍 전부 실패).
정답 쪽 `resolveSoundArrivalPortal`도 직선이 아니라 포탈 체인의 첫 문을 쓴다.

### 기억이 재현율을 두 배로 만든다

문턱을 매 감지마다 새로 만들면 벽면이 삭을 때 문턱도 사라져 방금 지나온 문도 잊는다.
`mergeThresholds`로 기억에 합치고 90초 동안 붙잡는다(문간은 움직이지 않는다).

| CQB 30초 × 5회 | 정밀도 | 팀 합산 문간 | 위치 오차 |
|---|---|---|---|
| 스냅샷 (기억 없음) | 84% | **3.2 / 7** | 5 px |
| 기억함 | 82% | **5.8 / 7** | 5 px |
| 기억함 + 모서리확정 게이트 | **98%** | 4.6 / 7 | 5 px |

**모서리확정 게이트**(양쪽 문설주가 확정된 모서리 = 그 너머를 실제로 봤다)는 사실상 공짜다 —
적 AI 평가 596회 중 이 게이트 때문에 문턱을 잃은 경우가 **1회**뿐이다. 소비자 기본값으로 쓴다.

### 방 이름 — 맵이 갖고, 관측으로 습득한다

`MAP_DATA.rooms`(CQB 9개: 방 A~D · 중앙 복도 · 현관 · 중앙실 · 3실 · 금고실).
좌표는 벽 저작 그대로다. **이름만 정답에서 온다** — 형상·문턱·클리어 여부는 전부 믿음이라
AI는 "방 B가 있다는 건 알지만 안이 어떻게 생겼는지는 모른다"를 표현할 수 있다.

```
named    이름만 안다 (문턱 너머로 들여다봤다)
entered  직접 들어가 봤다
cleared  들어가서 링이 닫혔고(다 봤다) 이 방 안에 보이는 적이 없다
```

상태는 역행하지 않는다. 실측(30초): 서 있는 방을 `entered`로 못 잡은 유닛 **0명**,
아는 방 수는 시간에 따라 증가(24→26), `named` 11 / `entered` 14 / `cleared` 2.

### 소음 귀속 — 정답 오라클과 대조

기존 `resolveSoundArrivalPortal`(정답 그래프)을 **손대지 않고 남겨 둬서** 공짜 오라클이 생겼다.

| 청취자-소음원 216쌍 | |
|---|---|
| 둘 다 문을 지목 → 위치 일치 | **50%** (오차 5 px 아니면 360 px로 이분) |
| 불일치의 원인 — 휴리스틱 실수 | **0건** |
| 불일치의 원인 — 정답 문을 몰랐음 | **8건** |

**일치율 50%는 결함이 아니다.** 불일치가 전부 "그 문의 존재를 몰랐다"이고, 아는 문 중
가장 그럴듯한 것을 고른 결과다. AI가 틀리는 게 이 설계의 목적이다 — 다만 일치율이 0이면
배선이 잘못된 것이다.

### 행동 둘 — 적 AI 전용

유틸리티 후보 8개 → 10개. `USE_BELIEF_ROOMS` + `unit.team === 'enemy'` 게이트.

- **`guardEntry`** — 내 방에 머물며 들어올 문을 경계. `preferredWatchAngle`을 문 방향으로
  놓으면 기존 조준 우선순위 사슬 6단계가 그대로 소비한다
- **`clearUnknownRoom`** — 아직 안 넘어간 문턱 앞으로 이동. 닫힌 문이면
  **이미 만들어 둔 `pendingDoor` 자동 개방이 이어받는다**

점수는 **정보의 질**로 매긴다. "소리가 저 문으로 들어왔다"는 "저쪽에서 소리가 났다"보다
훨씬 강한 정보라, 귀속이 있을 때만 `holdAngle`(방향만 보는 일반 경계)을 이기는 값을 준다.
귀속이 없으면 낮게 남아 대개 지는 게 맞다.

| CQB 30초 × 3회 | 귀속 가중 전 | 후 |
|---|---|---|
| `guardEntry` 채택 | 6 | **34** |
| `clearUnknownRoom` 채택 | 1 | **13** |

스위치 OFF에서는 적 후보가 **정확히 8개**이고 두 행동 채택 **0회** — 오늘과 완전히 동일하다.

### 점검

```js
GAME.beliefRoomsOn = false           // 런타임 A/B (const만으로는 계측이 안 된다)
GAME.debugSpatialMemory = true       // 벽(초록) / 문턱(청록 실선) / 프론티어(보라 점선) + 방 이름·상태
SpatialPerception.thresholdsOf(u)              // 확정 문턱만
SpatialPerception.thresholdsOf(u, {all:true})  // 미확정 포함
SpatialPerception.thresholdForNoise(u, x, y)   // 이 소리는 어느 문으로 왔나
```

> 범위 밖: `resolveSoundArrivalPortal`/`portalDangers`/`getSpatialRegionAt` 이관,
> 아군 AI 적용, 방 이름의 무전 전파, HFSM/GOAP.

## 벽 관통 — 믿는 재질로 쏜다

관통 **판단**은 원래부터 있었다. `classifyBarrierShotOpportunity`가
`wall_penetration` / `barrier_probe` / `no_shot`으로 나누고, 숙련도·기억 신뢰도·두께·재질로
조건을 걸고, 벽 뒤 아군 위험까지 검사해 보류한다. `barrierKnowledge`(관통 시도 결과, 20초 감쇠)도 있다.

없던 건 **입력**이다. `findFirstBarrierBetween`이 `obj.material`/`obj.armor`를 정답에서 읽어서,
AI는 판단은 제대로 하되 벽을 완벽하게 알고 했다. 이제 갈랐다:

```
기하  — "저기 뭔가 있다"        정답  (보면 안다)
재질  — "저건 콘크리트다"       믿음  (틀릴 수 있다)
두께  — "10 cm쯤 된다"          믿음  (양면을 봐야 안다. 모르면 겉보기 기하값)
장갑  — 재질 × 두께로 어림      믿음  (저작된 armor 수치는 사수가 읽을 수 없다)
```

재질이 우연히 맞아도 장갑은 **항상 다시 어림한다.** 맵에 적힌 `armor: 55`는 설계자가 적어 둔
값이지 벽을 보고 읽히는 게 아니다. 실제 탄환 물리는 이 경로를 쓰지 않는다 — **물리는 계속 정답**이라
AI가 틀렸다는 사실이 드러난다.

### 실증 — 오인이 방아쇠를 바꾼다

CQB 30초 × 3회, 장벽이 놓인 (사수, 표적) 232쌍을 정답 판단과 믿음 판단으로 각각 돌려 비교:

| | |
|---|---|
| 재질 오인 | 9 (3.9%) — 전부 `drywall → concrete` |
| **사격 판단이 뒤집힘** | **11 (4.7%)** |
| └ 재질을 오인해서 | **9** — 오인이 나면 **100% 판단이 바뀐다** |
| └ 재질은 맞췄지만 장갑을 어림해서 | 2 |
| 판단 변화의 내역 | `wall_penetration → no_shot` 9, `barrier_probe → no_shot` 2 |

**뒤집힘이 전부 한 방향이다** — 언제나 더 조심스러워지고, 근거 없이 대담해지지 않는다.
`MAT_LOOKALIKE`(석고↔콘크리트, 석고↔목재)가 무른 것을 단단한 것으로 착각하는 방향이고,
증거가 없으면 콘크리트로 단정하기 때문이다.

즉 **"석고보드를 콘크리트로 오인해서 뚫을 수 있는 벽을 안 뚫는다."** 처음에 세운 목표가
드디어 방아쇠까지 닿았다.

> 정직하게 덧붙이면, 실제 플레이 30초에서 장벽 사격 판단 61회 중 오인 위에서 내려진 게 8회였고
> 결과 분포는 크게 안 움직였다(`barrier_probe` 21.2% → 23.0%, 생존 동일).
> 배선은 실재하고 반사실 분석에서 100% 뒤집히지만, 이 맵·이 시간 규모에서 **눈에 띄는 총량 변화는 작다.**
> 더 크게 만들려면 맵 내용이나 관통 문턱을 손봐야 하고, 그건 배선이 아니라 별개 문제다.

### 점검

```js
GAME.beliefBarrierOn = false    // 런타임 A/B
SpatialPerception.believedBarrierAt(unit, x, y)   // 이 자리 장벽을 뭐라고 믿나
debugShootThroughBarrier('OPFOR-1','Alpha-1')     // 진단 콘솔은 계속 정답을 본다
```

## 맵에 우회로 — 선택지가 없으면 전술도 없다

위험 가중 경로가 값을 못 한 이유는 알고리즘이 아니라 **맵 형태**였다.
북쪽 방 넷과 남쪽 방 넷을 잇는 통로가 「중앙 복도」 하나뿐이었고, 그게 통짜라
남북 횡단로가 넷이나 있어도 **전부 같은 방**이었다. 어디로 건너든 위험이 똑같으니 고를 게 없다.

두 가지를 냈다:

| | |
|---|---|
| **복도 분절** | 방화문 격벽 둘(x=520 / x=1100) → 서쪽·중앙·동쪽 복도 |
| **측면 통로** | 방 A↔방 B (x=414), 중앙실↔3실 (x=900) — 복도를 안 거치는 두 번째 길 |

문은 넷 → **일곱**. 격벽 문은 강철(서쪽 열림 / 동쪽 닫힘), 측면 문은 목재.

### 효과

위험 섹터가 갈렸다. 전에는 전 유닛이 통짜 복도 하나만 뜨겁다고 봤는데,
이제 아군은 「서쪽 복도」를, 적은 「현관」을 뜨겁다고 본다 — **"저쪽은 조용하니 그리로 건넌다"가 성립한다.**

짝지어 비교(같은 상황에서 두 방식 모두 계산, 5회 × 30초, 경로 15,888건):

| | 우회로 전 | 우회로 후 |
|---|---|---|
| **더 안전해진 경로** | 15 | **106 (7배)** |
| 더 위험해진 경로 | 0 | **0** |
| 위험 적분 | −3.6% | **−5.6%** |
| 경로 길이 | ±0% | ±0% |
| `findPath` 비용 | 1.9배 | 1.9배 |

그래서 **`USE_DANGER_PATH_COST`를 다시 켰다.**

> 「절대 더 나쁜 길을 내놓지 않는다」를 위해, 위험을 지나는 경로에 한해 후보를 모두
> 총비용(길이 + 위험 적분)으로 재고 고른다. 위험을 아예 안 지나면 비교할 게 없으니 건너뛴다 —
> 대부분이 그 경우라 두 번째 탐색 비용이 거의 안 든다.

### 픽스처가 또 지형에 걸렸다

맵을 바꿀 때마다 같은 자리에서 하네스가 깨진다. 이번엔 셋:

- `B-12` — "이 두 점은 같은 방" 픽스처가 **실제로 틀렸다.** 복도를 나눴으니 기대값을 고쳤다
- `C1-02` — 픽스처 벽 선택기가 **전체 관측 구간만** 확인해서, 좁은 구간(60~160)이 하필
  새 격벽에 걸리는 벽을 통과시켰다. 테스트가 쓰는 구간을 전부 확인하게 고쳤다
- `C1-13` — 앞 시험(C1-12)의 유닛이 **같은 자리에서 슬롯을 예약한 채 살아 있어** 후보가 0이 됐다.
  이 시험은 플레이어 명령 권위를 보는 것이지 슬롯 경쟁이 아니므로 앞선 예약을 지우고 시작한다.
  덤으로 맵을 편집하는 `C1-10`이 **스스로 되돌리게** 했다

교전 카나리아(스위치 OFF에서 초기 교전이 나는가)는 4회 중 3회 발생 — 통과.

## 위험 섹터 — 위험은 방 단위다

처음엔 반경으로 칠했다. **반경은 벽을 무시한다** — 실측: 위험 비용이 붙은 셀의 **36.6%**가
위험원과의 사이에 벽이 있었다. 옆방 총성이 벽을 뚫고 내 안전한 방까지 비용을 칠하고 있었다.

위험은 "총 맞을 수 있는 공간"의 성질이고, 그 공간을 가르는 건 방이다. 그래서 방 단위로 옮겼다.

```
mem.roomDangers: Map(roomId → { level, lastAt })
  총성을 들은 방   레벨  9   ← 추정 위치(오차 포함)를 방에 귀속
  적을 본 방       레벨 14
  폭발             국소로 남긴다 (방보다 작고 방 한가운데서 난다)
```

방 안에서 균일하고 경계에서 계단처럼 오른다. 그게 맞다 — **위험을 감수하는 행위는 문턱을 넘는 것**이라,
안전한 방과 뜨거운 방 사이의 문턱이 저절로 비싼 칸이 된다.
방이 저작 안 된 맵은 예전 반경 모델로 폴백한다.

### 경로 소비는 기본 OFF — 이 맵엔 우회로가 없다

모델은 제대로 돈다. 실측(30초): 위험 섹터가 실제로 표시되고 레벨 2.8~13.9로 감쇠한다.
그런데 **거의 모든 유닛이 뜨겁다고 보는 방은 「중앙 복도」 하나**다 — 교전이 다 거기서 나니까.
그리고 그 복도는 **북쪽 방들과 남쪽 방들을 잇는 유일한 통로**다. **피할 길이 없으면 A*가 고를 것도 없다.**

| 짝지어 비교 (같은 상황에서 두 방식 모두 계산, 경로 7,555건) | |
|---|---|
| 더 안전해진 경로 | 15 (0.2%) |
| **더 위험해진 경로** | **0** |
| 위험 적분 | −3.6% |
| 경로 길이 | ±0% |
| `findPath` 비용 | 0.097 → 0.185 ms (1.9배) |
| 프레임 p95 | 18.5 → 23.2 ms |

이 결과는 **복도가 통짜였을 때**의 것이다. 위 「맵에 우회로」에서 복도를 셋으로 나누고
측면 통로를 낸 뒤 재측정해 `USE_DANGER_PATH_COST`를 다시 켰다.

> 여기서 실험 설계를 두 번 고쳤다. 처음엔 **회차를 나눠** 비교했는데 교전량이 회차마다 달라
> 위험장 자체가 달라져서 지표 변동이 효과보다 컸다(OFF가 11.5·15.6·54.8로 튀었다).
> **같은 상황에서 두 방식을 모두 계산해 짝지어야** 답이 나왔다.
> 그리고 처음엔 A*를 맹목적으로 선호해서 **더 위험해진 경로가 124건 vs 안전해진 46건**이었다 —
> 직선 지름길을 막으면 격자 경로가 길어지고, 우회할 다른 방이 없으면 길이만 늘어 총 위험이 커진다.
> 두 후보의 **총비용(길이 + 위험 적분)을 재서 나은 쪽**을 고르게 하니 더 위험해진 경로가 0이 됐다.

### 행동이 위험 섹터를 쓴다

경로보다 여기가 값을 한다. `beyondRoomDanger(unit, threshold)` — 이 문 너머 방이 얼마나 뜨거운가.

- `guardEntry` — 문 너머가 뜨거우면 **+10** (저기로 들어온다)
- `clearUnknownRoom` — 뜨거운 방으로는 **−22** (우세하면 −8로 완화)

| CQB 30초 × 3회 | 섹터 적용 전 | 후 |
|---|---|---|
| `guardEntry` 채택 | 34 | **60** |
| `clearUnknownRoom` 채택 | 13 | **4** |

방어자가 뜨거운 복도로 나가는 대신 **자기 방에서 그쪽 문을 지킨다.** 의도한 전술이다.

### 점검

```js
GAME.dangerPathOn = true                   // 경로 소비를 켠다 (기본 꺼짐)
buildDangerField(unit)                     // { rooms, roomW, local }
beyondRoomDanger(unit, threshold)          // 이 문 너머 방이 얼마나 뜨거운가
```

## 위험 가중 경로 — 지르지 않고 돌아간다

"위험지역을 가로지르는 리스크"를 **경로 비용**으로 표현한다. 막지 않고 비싸게 만든다 —
급하면 지르고 여유가 있으면 돌아가는 판단이 A* 안에서 저절로 나온다.

문 비용 때문에 뚫어 둔 `_pathPredicates`의 `cellCost` 이음매를 그대로 쓴다.
위험원은 **전부 이미 유닛별 기억**이라 정답에서 새로 읽는 게 없다:

| 위험원 | 출처 | 반경 | TTL | 가중 |
|---|---|---|---|---|
| 총성 위험구역 | `mem.noiseDangerZones` (들은 것) | 기록된 반경 | 18초 | 9 |
| 폭발 지점 | `mem.dangerPoints` | 3 m | 15초 | 12 |
| 마지막으로 본 적 | `mem.lastSeenEnemy` | 6 m | 25초 | 14 |

중심에서 가장 비싸고 가장자리에서 0(선형). 한 칸 이동 비용이 1.0이니 위험 중심은 대략
**9~14칸을 돌아갈 만한 값**이다. 겹쳐도 상한(26)을 넘지 않는다.
플레이어가 그은 경로는 `unit` 없이 `findPath`를 부르므로 위험 가중이 안 붙는다 — 의도한 대로다.

### 구멍 둘을 먼저 막아야 한다

`cellCost`만 얹으면 아무 일도 일어나지 않는다. **A*를 우회하는 경로가 둘 있다.**

1. **직선 지름길** — `hasLineOfWalkClear`가 통과하면 A*를 아예 안 돌린다.
   위험구역을 가로지르는 직선이 그대로 채택된다
2. **경로 단순화** — `simplifyPath`가 A*가 애써 돌아간 길을 다시 곧게 편다

둘 다 `segmentDangerCost`(선분 위 평균 위험)로 막았다. 평균이라 길이에 비례해 커지지 않는다.

### 피하려다 못 움직이면 더 나쁘다

위험 비용은 탐색을 목표지향에서 멀어지게 한다 — 휴리스틱은 거리만 보는데 g는 위험까지
싣기 때문이다. 그래서 `MAX_ITER`를 소진해 **경로 실패가 생겼다(0 → 36건 실측).**

두 겹으로 막았다:

```
A* 실패 → 위험을 빼고 한 번 더 찾는다 → 그래도 없으면 직선이 뚫려 있었는지 본다
```

**위험 가중은 선호지 금지가 아니다.** 재측정 결과 실패 0건.

> 이 절의 반경 모델은 **위 「위험 섹터」로 대체됐다.** 아래 설계(구멍 둘 막기, 실패 방지)는
> 방 단위에서도 그대로 유효하다.

## 경로 탐색 — 병목이 어디였나

A\* 교체(Theta\*/D\*)를 검토하다 프로파일부터 냈다.

```
findPath 4,744회 / 30초
  직선 지름길로 끝남 (2점)  2,568  54.1%   ← 격자를 아예 안 씀
  A* 격자 탐색               2,176  45.9%   ← 평균 웨이포인트 2.92개
총 경로 시간 = 프레임의 1.3%
```

**경로 탐색은 병목이 아니다.** 그리고 호출자를 세어 보니 답이 나왔다:

| 호출자 | 횟수 |
|---|---|
| `buildObservedCoverSlotCandidates` | **4,128 (96%)** |
| `issueMoveOrder` | 28 |
| `findNearbyCover` | 4 |

이동이 아니라 **엄폐 슬롯 도달성 검사**였다. 슬롯은 다 가까이 있어서
**직선이 뚫려 있으면 경로 길이는 정확히 직선거리다**(근사가 아니라 동일).
막혔을 때만 A\*를 돌리게 하니 **A\* 실행 4,744 → 2,288회**.

> 위험 가중이 켜져 있으면 A\*가 직선을 놔두고 우회할 수 있어 길이가 어긋난다 — 그때는 지름길을 쓰지 않는다.

**시도했다가 되돌린 것**: 경로 캐시. "같은 목표 재계획 4,492회 / 서로 다른 목표 252개"를 보고
캐시를 넣었는데 적중률이 **0.2%**였다. 키에 시작 셀이 들어가는데 유닛이 걸어가니 매번 달라진다.
그 비율은 중복 계산이 아니라 "여러 유닛이 몇 안 되는 목표로, 매번 다른 위치에서" 물은 것이었다. 되돌렸다.

### 왜 Theta\* / D\*가 아닌가

- **Theta\*** — 54%가 격자를 안 거치고, 나머지도 `simplifyPath`가 이미 string-pulling으로 펴 둔다.
  기하는 거의 같은 게 나온다. 진짜 값은 **공간마다 비용이 다를 때**(위험 가중) 격자 A\* + 사후
  평활화의 불일치를 없애는 것인데, 그 위험 가중을 지금 껐다. 대체 경로가 있는 맵을 만들 때 다시 볼 것
- **D\*** — 유닛마다 자기 믿음 지도가 있고 관측할 때마다 바뀌어 탐색 트리가 계속 무효화된다.
  게다가 최적화 대상이 프레임의 1.3%다

## 벽 미끄러짐 — 막혔다고 경로를 버리지 않는다

이동 중 막히면 **경로를 통째로 포기했다**(`벽에 막힘. 경로 종료.`). 모서리에서 계속 멈춰 섰다.
이제 축을 분리해 갈 수 있는 쪽으로 미끄러진다. 물리는 그대로 정답을 본다 — 통과시키는 게 아니라
갈 수 있는 축으로만 보낸다.

| CQB 30초 × 4회 | 이전 | 이후 |
|---|---|---|
| 경로 포기 | ~12.8/회 | **~2.3/회 (−82%)** |
| 벽 미끄러짐 | — | 584 (4회 합계) |
| 갇힘 | 0 | 0 |

미끄러지는 내내 매 프레임 접촉을 심지는 않는다 — 같은 벽을 문지르는 것뿐이라 기록할 새 사실이 없다.
0.5 m를 옮겼거나 0.5초가 지났을 때만 남긴다(심은 표면 323.7 → 4.3).

## 유틸리티 AI — HFSM을 재다가 다른 걸 찾았다

계층(HFSM)을 넣기 전에 **무엇이 실제로 약한지** 쟀다. 처음 근거로 들었던
"다단계 의도가 0.4초 재평가에 잘린다"는 **측정에 나오지 않았다** —
행동 전환의 대부분이 `holdAngle → engageEnemy`, 즉 적이 나타나서 바꾼 **정당한 중단**이었다.

대신 나온 것:

| 행동 평가 2,481회 (30초 × 3) | |
|---|---|
| **1·2위 점수차 < 점수 노이즈 폭** | **867회 (36%)** |
| 1위 분포 | `holdAngle` 64% |

**그 결정들은 상황이 아니라 난수가 골랐다.** 그리고 결정적으로,
**행동이 완료된 시점에는 전환 문턱 검사가 없다**(`if (!aiAction || curActionDone) shouldSwitch = true`).
그래서 그 난수가 매 행동 경계마다 그대로 다음 행동이 된다.

### 자세 계층은 이 문제를 못 고친다

가설을 세워 먼저 재 봤다 — 후보를 자세(FIGHT/WATCH/PUSH)로 묶으면 동전던지기가 갈릴까?

```
동전던지기 867건 중
  다른 자세끼리   119  (14%)   ← 계층이 없앨 수 있는 것
  같은 자세 안에서 748  (86%)   ← 계층으로도 안 없어짐
```

**86%가 같은 자세 안**이었다. 내역을 보니 이유가 분명했다:

```
guardEntry vs holdAngle          401
holdAngle vs repositionToCorner  216
repositionToCorner vs guardEntry  92     →  867건 중 ~709건 (82%)
```

셋 다 **"제자리에서 지켜본다"의 변형**이다. 자세로 묶어 봐야 같은 자세라 안 갈린다.

### 그래서 넣은 것 — 하던 일을 동전던지기로 바꾸지 않는다

직전에 하던 행동이 아직 후보에 있고 1위와의 차이가 **점수 노이즈 폭 안**이면 그걸 유지한다.
점수가 의미 있게 벌어졌을 때만 갈아탄다. `USE_UTILITY_STICKY`, 창 2초.

| CQB 30초 × 3회 | OFF | ON |
|---|---|---|
| **지켜보기 변형끼리 갈아타기** | 71 (변경의 58%) | **44 (33%)** |
| `guardEntry` 평균 지속 | 4.6 s | **15.6 s** |
| `engageEnemy` 실행 | 27 | **53** |
| `seekCover` 실행 | 9 | **44** |
| 갇힘 | 0 | 0 |

대원이 문을 **실제로 지킨다**(4.6초 → 15.6초). 그러면서 적이 보이면 여전히 교전하고,
오히려 결정적인 행동(교전·엄폐)이 늘었다 — 난수 churn에 낭비하던 판단이 제자리를 찾은 것이다.

> 적용 자체는 30초에 22회뿐인데 효과가 큰 이유는, 한 번의 뒤집힘이 연쇄를 만들기 때문이다.
> 문턱 검사가 없는 완료 시점에 잘못 갈아타면 그 행동이 또 완료되며 다음 뒤집힘을 낳는다.

**HFSM은 아직 넣지 않았다.** 넣을 근거가 측정으로 서지 않았고, 세우려던 계층은
문제의 14%만 건드렸다. 표현 못 하는 의도가 실제로 쌓이면 그때 다시 볼 것.

### 아직 정답 기반인 것

| 항목 | 이유 |
|---|---|
| `knownRegions`/`knownPortals` | **시도했다가 껐다** — 아래 참조 |
| 적 탐지 (`castScanRay`) | prone 반높이 밀착·peek 깊이·표적 자세 규칙이 205줄 중 큰 비중. 위상 이관과 한 덩어리 — `castScanRay` 호출 5,186회 중 포탈 추적이 5,178회라 위상이 넘어가야 이 레이 패스를 지울 수 있다 |
| ~~`findFirstBarrierBetween`~~ | **이관 완료** — 아래 「벽 관통 — 믿는 재질로 쏜다」 참조 |
| 물리 전반 | 의도적. 위 경계선 참조 |

### 점검 / 진단

```js
SpatialPerception.runSelfTests()        // 64/64 통과해야 함
SpatialPerception.measureAll(UNITS)     // 전 유닛 인식 오차 집계
SpatialPerception.measureAccuracy(u)    // 유닛 1명
GAME.debugSpatialMemory = true          // 믿는 지형 오버레이 (붉은 구간 = 허상)
```

`measureAll`은 정답 지오메트리와 대조하므로 **진단 전용**이다. AI 판단 경로는
절대 호출하지 않는다. 주요 지표:

| 지표 | 뜻 |
|---|---|
| `phantomRate` | 믿는 벽 길이 중 실재하지 않는 비율 |
| `worstPhantomPx` | 한 면에서 가장 긴 허상 구간 |
| `ghostRate` | 절반 넘게 허상인 면의 비율 |
| `reconcileSplits/Kills` | 반증이 기억을 쪼갠/지운 횟수 |
| `thicknessRate` | 양면 관측으로 두께를 얻은 면의 비율 |
| `materialWrongRate` | 믿는 재질이 실제와 다른 면의 비율 |
| `materialClassWrongRate` | 등급까지 틀린 비율 (낮아야 함) |
| `materialExactRate` | 정확한 재질까지 아는 면의 비율 |
| `byTier` | 숙련도별 분해 |

> `byTier`의 비율만 보면 오해한다. 아는 면이 적을수록 "가진 것 중 정확한 비율"은
> 높아지므로, recruit이 elite보다 정확해 **보인다**. 규모(`believedPerUnit`)를 같이
> 봐야 적게 아는 것과 정확히 아는 것이 구분된다.

기존 시스템은 정의상 이 값들이 전부 0이다. **0이 아니게 되는 것이 교체가
동작한다는 증거**다.

> 끝점의 수직오차나 실제 면 밖으로 삐져나간 길이를 재면 안 된다. 관측점이 정답
> 선분 위에서 생성되므로 그 두 값은 구조적으로 항상 0이며, "오차 없음"이라는
> 잘못된 결론이 나온다.

### 성능

관측자당 약 0.5ms. `getScanProfile`의 숙련도별 `scanInterval`(0.22~0.6초)에
얹고 유닛마다 해시 위상 오프셋을 줘 같은 프레임에 몰리지 않게 한다. 프레임당
2.5ms 예산을 초과하면 다음 프레임으로 미룬다. 14명 실측 0.3~0.6ms/프레임.

## 수류탄 — 누가 던졌나는 놀람을, 얼마나 가까운가는 도망을 정한다

AI 투척을 붙이기 전에 **아군이 던진 수류탄이 팀에 무슨 짓을 하는지** 먼저 쟀다.
아군 하나가 앞으로 8 m 던지게 주입하고 세었다:

| 30초 주입 × 3회 | 이전 | 이후 |
|---|---|---|
| 던진 본인이 자기 수류탄을 위험으로 본 tick | 0 / **28** / 0 | **0 / 0 / 0** |
| 던진 본인 행동 파기 | 28회 | **0** |
| 팀원 반응 (3명 중) | **3 / 3 / 3 매번 전원** | 0~3, 전부 `evade` |
| 팀원 행동 파기 | 27회 | 0 |
| 적 반응 | 2~3 | **2~4 (유지)** |

원인은 같은 판정을 **층 둘이 다른 규칙으로** 하고 있었다는 것이다.

| 층 | 팀 인식 | 기준 |
|---|---|---|
| `perceiveGrenades` (물리 회피) | 있으나 약함 | 무시하려면 *예상착탄 멂 && 안 다가옴 && 최근접 안전* 셋 다 |
| `getGrenadeDangerForUnit` (유틸리티 위험) | **없음** | 신관 1.2초 + 6 m |

그래서 옆을 스쳐 날아가기만 해도 팀 전원이 엎드렸고, 던진 사람도 예외가 아니었다.

이제 두 층이 `blastHarmAt` 하나를 공유한다 — 착탄점, 실제 피해 반경, LOS 차단으로
0~1 위해를 낸다. 그 위에 규칙이 둘뿐이다:

- **누가 던졌나**(`mine` / `friendly`)는 **놀람**만 없앤다 — 패닉 제거, 반응 지연 0.45배,
  엎드리기 대신 반경 밖으로 비켜서기, 경보 로그·FX도 조용한 쪽으로
- **위해 추정**은 그대로 도망시킨다 — `harm ≥ 0.55`면 자기 수류탄이라도 회피

측정 중에 그 두 번째 규칙이 실제로 걸린 장면이 나왔다: 벽에 튕겨 **자기 발밑 0.3 m**에
떨어진 자기 수류탄(`harm 1.0`) — 던진 사람이 정확히 도망쳤다. 이전 코드에서는 이 경우가
8 m 앞에 던진 것과 구별되지 않았다.

파편 항은 제곱 감쇠다. `fragmentRadius`(M67 = 18 m)는 사상 반경이지 치명 반경이 아닌데
선형으로 두니 8 m 떨어진 아군까지 0.25가 나와 "알고 있는 수류탄"에도 전원이 반응했다.

### 던지기 전에 막는다

`checkThrowSafety`는 **실제로 던질 때와 같은 궤적 시뮬**을 돌려 튕김까지 반영한 착탄점에서
자기 위해(> 0.15)와 아군 위해(> 0.25)를 본다. 조준점이 아니라 착탄점이라는 게 핵심이다 —
자체테스트 중 벽에 되튕겨 발밑에 떨어지는 투척이 실제로 걸렸다.

플레이어 투척은 이 게이트를 통과하지 않는다. 발밑에 굴리는 것도 선택이다.

스위치는 `USE_GRENADE_OWNER_AWARE` / `GAME.grenadeOwnerAwareOn`. 끄면 오늘과 동일하고,
적이 던진 수류탄 경로는 스위치와 무관하게 언제나 그대로다(자체테스트로 고정).

## 피킹 — 의도적 관측

지금까지 믿음은 전부 **돌아다니다 우연히 본 것**의 부산물이었다. 피킹은 다르다 —
모르는 걸 알기 위해 위험을 감수하고 정보를 얻으러 나갔다 돌아온다.

구조에 없던 건 각도도 자세도 아니라 **왕복**이었다. 지금 모든 행동은 목표에 닿으면 끝난다.

```
나감(out) → 관측 창(look, 0.4~0.9초) → 복귀(back)
```

계약은 하나다: **어떻게 끝나든 원위치로 돌아온다.**

### 한 발은 아무것도 안 보여준다

처음엔 제자리에서 문턱 쪽으로 **1 m만** 내밀게 했다. 결과가 나오지 않았다 —
레이 스캔이 이미 그 각을 다 보고 있었기 때문이다. 문설주에 가려 있는 한 한 발로는 각이 안 열린다.

노출 지점을 **개구부 정면**(문턱 앞 1 m, 법선 방향 내 쪽)으로 옮겼다. 실제 "파이 자르기"다.

| 30초 × 4회, 피킹 43회 | 한 발 내밀기 | 개구부 정면 |
|---|---|---|
| 피킹당 새로 알게 된 표면 | 1.18 | **4.28** |
| 이득이 0인 피킹 | 36% | **28%** |
| 새 문턱 / 새 방 (합계) | 1 / 1 | **13 / 11** |
| 피킹 중 피격 | 0% | **0%** |
| 완주한 피킹의 복귀율 | 100% | **100%** |
| `stuckInsideGeometry` | 0 | **0** |

중간에 끊긴 35%는 전부 `other_order` — AI가 다른 데로 가기로 한 정상 취소다.
왕복 제한시간은 거리에 맞춰 늘어난다(고정 5초로 두니 먼 피킹이 통째로 시간초과로 끝났다).

> 다만 정직하게 적어 둔다. 피킹이 **적을 발견한 비율은 9%**다. 지금 피킹이 버는 건
> 주로 지형이지 접촉이 아니다. 이 행동의 값은 "본 것으로 다음 결정을 바꾼다"에서 나와야 하고,
> 그건 아직 배선되지 않았다.

### 왜 점수를 올리지 않았나

후보로 오른 155회 중 피킹이 이긴 건 12회(8%)다. `holdAngle` 72회, `guardEntry` 65회에 졌다.
낮아 보이지만 **측정으로 정당화되지 않은 가산은 넣지 않는다** — 값을 올릴 근거는
"본 것으로 결정이 바뀐다"를 보인 다음에 생긴다.

스위치는 `USE_PEEK` / `GAME.peekOn`. 팀 게이트는 없다 — 의도적 관측은 팀을 안 가린다.

## 프래그 후 진입 — 0.4초 재평가로는 안 되는 첫 의도

```
look → decide → throw → wait → enter
       ↑ 피킹이 여기서 처음으로 결정을 바꾼다
```

준비 0.6초 + 비행 + 신관 4.7초 ≈ 6초, 재평가 **열네 번**. 유틸리티만으로는
던지자마자 다른 행동으로 갈아타고 수류탄은 아무도 안 보는 방에서 터진다.
그래서 계획을 예약(`pendingFrag`) 하나로 들고 가고, 예약이 살아 있는 동안은
점수로 갈아타지 않는다(`plan_in_progress`). 놓아 주는 조건은 둘뿐이다 —
**수류탄 위험**과 **중상**. 살자고 그만두는 건 막지 않는다.

### 팀은 측정이 정했다

0.5초 표본 2,439건에서 "안 넘어간 문턱이 있고 그 너머가 뜨겁다"가 나온 비율:

| | 표본 | 해당 | 비율 |
|---|---|---|---|
| 적 (방어) | 1,719 | 16 | **0.9%** |
| 아군 (돌입) | 720 | 577 | **80.1%** |

방 위험은 **뭔가를 지각한 방**에만 찍히는데, 안 넘어간 문턱 너머는 정의상
지각한 적 없는 방이다. 두 집합이 겹치는 건 밀고 들어가는 쪽뿐이다.
그래서 이 행동은 `guardEntry`/`clearUnknownRoom`과 반대로 **아군 전용**이다.

### 네 번 틀리고 고친 것

| 증상 | 실제 원인 |
|---|---|
| 대상의 대부분이 잘려 나감 | 거리 상한 9 m인데 문턱까지 **중앙값이 10 m**였다 (217/242 탈락) → 15 m |
| `approach_timeout`이 6건 중 4건 | 접근 제한을 **누적 시간**으로 쟀다. 피킹 왕복(최대 10초)만으로 이미 초과 → 단계별 타이머 |
| `no_throw_spot` — 후보 18개 전부 탈락 | 뜨거운 방 문턱 옆은 언제나 `tacticalInvalid`다. **던질 만한 방일수록 던질 자리가 없어진다** → 물리적 유효성만 본다 |
| `unsafe_self_blast`가 절반 | `computeAutoCornerLaunch`가 **facing** 기준으로 발사점을 옮긴다. 몸이 딴 데를 보고 있으면 자리 고를 때 통과한 궤적과 실제 궤적이 달라져 문틀에 튕겨 돌아왔다 → 던지기 전에 조준점 쪽으로 돈다 |
| 진입하다 말고 되돌아옴 | `_peekProbe`가 **현재 위치** 기준으로 '너머'를 정한다. 문턱을 넘는 순간 목표가 반대편으로 뒤집혔다 → 진입 목표를 `decide`에서 굳힌다 |

던질 자리는 하나가 아니라 **좌/우 × 이격 × 후퇴 조합을 실제 궤적 시뮬로 검사해
안전한 순서로 정렬한 목록**이다. 경로가 없거나 위해가 크면 다음 자리를 쓴다.

### 지금 어디까지 되나

기계는 끝까지 돈다 — `look→decide→throw→wait→enter→done`이 완주하고,
**내부 중단(abort) 0건, 자해 0, 갇힘 0**이다.

그러나 **실전에서는 거의 완주하지 않는다.** 추적이 이유를 그대로 보여준다:

```
{"phase":"throw","reason":"switched_to_seekCover","hp":45}
{"phase":"throw","reason":"switched_to_seekCover","hp":38}
{"phase":"throw","reason":"switched_to_seekCover","hp":33}
```

**던질 자리로 걸어가는 동안 총에 맞는다.** 방을 뜨겁다고 믿게 만든 그 적이
아직 살아서 쏘고 있기 때문이다. 그러면 `seekCover`가 100점 넘게 앞서고,
계획 유지 조건(중상)도 정직하게 풀린다. 이건 계획의 버그가 아니라
**이 맵에서 아군 4명이 적 8~10명을 상대로 지고 있다**는 사실이다.

> 그래서 남은 일은 프래그 쪽이 아니라 접근 쪽에 있다 — 사선을 피해
> 벽을 타고 문 옆에 붙는 스택업. 지금은 문 앞 공터를 가로질러 간다.

스위치는 `USE_FRAG_PLAN` / `GAME.fragPlanOn`. 남발 방지는 세 겹이다 —
1인 1발, 방당 1회(`FRAG_ROOM_COOLDOWN` 45초), 그리고 조용한 방(`danger ≤ 0.5`)에는
계획 자체를 세우지 않는다.

## 치명적 깔때기 — 경로는 바꿨는데 결과가 안 바뀐다 (`USE_FUNNEL_COST = false`)

프래그 계획이 **던질 자리로 걸어가다 총에 맞는다**는 걸 hp 추적으로 보고, 그게 실제로
얼마나 되는지 쟀다. 아군 경로 396건에서 **뜨거운 방으로 뚫린 사선 안을 지나는 길이**:

| 행동 | 경로 | 사선 노출 |
|---|---|---|
| `fragThenEnter` 접근 | 247 | **75.0%** |
| 피킹 | 98 | 36.8% |
| `seekCover` | 35 | 31.7% |
| 전체 | 396 | **40.5%** |

원인은 분명했다. **위험은 방 단위인데 노출은 사선 단위다.** 문 앞 공터는 다른 방이라
위험장에서 싸지만, 거길 지나면 뜨거운 방 안에서 그대로 보인다.

그래서 스택업을 새 행동으로 만들지 않았다 — **깔때기를 비싸게 만들면 경로가 알아서
벽을 탄다.** 문설주 옆은 사선 밖이니 A*가 거기로 붙는다. 판정은 레이캐스트가 아니라
문턱 게이트와의 **선분 교차** 하나다(셀마다 도는 계산이라).

### 가중치는 쓸어서 골랐다

짝지은 A/B — 같은 findPath 호출에서 양쪽을 다 계산해 회차 변동을 지웠다:

| W | 총 노출 | 경로 길이 | 개선 / 악화 | findPath |
|---|---|---|---|---|
| 0.05 | −7.6% | +0.3% | 569 / 58 | 1.24배 |
| **0.15** | **−19.7%** | +7.6% | **926 / 122** | 1.72배 |
| 0.35 | +5.5% | +25.3% | 663 / 757 | 2.70배 |
| 1.1 | +28.1% | +62.9% | 702 / 1873 | 3.03배 |

비싸게 매길수록 노출**률**은 계속 좋아지는데(60.9% → 51.3%) **총 노출은 오히려 늘어난다.**
경로가 그만큼 길어지기 때문이다. 위험 가중 경로에서 배운 것과 같다 —
지표는 비율이 아니라 **적분**이어야 한다.

### 그런데 결과가 안 움직인다

경로 지표만 보면 채택할 만하다. 그래서 실제 결과를 쟀는데:

| 30초 × 26회 | 아군 생존 (4명 중) | 아군 피해 |
|---|---|---|
| OFF | **2.69** | 155 |
| W=0.15 | **2.62** | 165 |
| W=0.15 + 미확인 문턱도 사선(base 5) | 2.67 | 162 |

전부 잡음 안이다. 처음 6회씩 잰 표본은 240 vs 129로 **두 배 차이**가 났는데,
같은 설정을 8회 더 재니 112로 뒤집혔다 — 회차 변동이 효과보다 크다.
아군 피해는 사실상 "4명 중 몇 명이 죽었나"라서 0~300 사이를 튄다.

그래서 **기본 OFF**다. `findPath` 1.72배를 내고 살 값이 아직 증명되지 않았다.
위험 가중 경로가 우회로 없는 맵에서 한동안 기본 OFF였던 것과 같은 처지고,
값을 하게 되는 조건이 생기면 그때 켠다.

> 왜 결과가 안 움직였을까에 대한 지금의 추측: 이 시나리오의 아군 사망은 **이동 중
> 노출**보다 **서서 주고받는 교전**이 지배한다. 그리고 깔때기는 방이 뜨겁다고 믿은
> **뒤에야** 생기는데, 그 시점이면 이미 접촉이 일어난 뒤다.

스위치는 `USE_FUNNEL_COST` / `GAME.funnelCostOn`, 가중치는 `GAME.funnelW`,
미확인 문턱 기본 위험은 `GAME.funnelBase`.

## 성향 — "무엇을 하고 싶나"

숙련도(`getUtilityProfile` / `getReactionProfile`)는 이미 있었다. 그런데 그건 **"얼마나 잘 하나"**다 —
elite는 점수 노이즈가 1이라 덜 흔들릴 뿐, recruit과 **원하는 게 같다.** 행동 간 선호는 전 유닛이
동일했고, 시나리오는 14명 전원 `regular` / 전원 `reactive`였다. 그래서 넷이 늘 같은 걸 했다.

축은 둘이다. 네 단어(적극/소극/신중/무모)를 4분류로 두는 것보다 넓다 —
"적극적이면서 신중함"(밀되 먼저 본다)과 "소극적이면서 무모함"이 둘 다 나온다.

| 축 | 올라가는 행동 | 내려가는 행동 |
|---|---|---|
| 공격성 | `clearUnknownRoom` +12 · `fragThenEnter` +10 · `engageEnemy` +8 | `retreatFromThreat` −10 · `holdAngle` −9 · `seekCover` −8 |
| 신중함 | `peekAndAssess` +10 · `seekCover` +9 · `goProne` +6 | `clearUnknownRoom` −4 · `engageEnemy` −3 |

점수 함수 12개를 각각 고치지 않고 **후보 조립 지점 한 곳**에서 얹는다. 끄면 항이 0이다.

### 다양성의 출처가 노이즈면 흩어지지 않는다

지금까지 유일한 다양성은 `scoreNoise`였는데, 노이즈는 **매 결정마다 다시 굴려서** 평균으로 수렴한다.
성향은 유닛에 붙어 계속 같은 방향으로 민다. 그 차이가 그대로 나왔다:

| 30초 × 6회 | 성향 OFF | 성향 ON |
|---|---|---|
| **아군 의도 중복** (2명 이상 같은 행동) | **39%** | **18%** |
| 아군이 퍼져 있는 방 수 (4명) | 1.35 | **1.57** |
| 적 `guardEntry` | 29% | 36% |
| 적 `clearUnknownRoom` | 0% | 1% |

다만 정직하게 — **`holdAngle` 지배는 못 풀었다**(57% → 58%). 성향은 뭉침을 풀었지,
"제자리에서 각 잡기"가 시간의 절반을 먹는 문제는 그대로다. 그건 다른 작업이다.

원형은 **번호 순서로 돌린다**. 완전 무작위로 굴렸더니 실행마다 팀 구성이 통째로 달라져서
같은 설정 두 번에 의도 중복이 10%와 33%로 나왔다 — 전투 변동 위에 구성 변동이 얹혔다.

### 성향이 드러낸 버그 둘

**① `investigateNoise` 실행부가 널을 읽고 크래시했다.** 이 파일에서 점수 0은
"지금 이 행동은 자격이 없다"는 뜻인데(`scoreInvestigateNoise`는 들은 소리가 없으면 0),
성향 가산이 그 0을 1위로 밀어 올렸다. 그러면 실행부가 없는 전제를 읽는다.

무행동(`aiAction === null`) 시간이 15~22%로 튀길래 수류탄 반응인 줄 알았는데,
잡아 보니 예외였다 — 한 실행에서 표본 1,218건 중 1,131건이 크래시 이후였다.
고친 건 둘 다다: **자격 없는 후보에는 편향을 얹지 않고**, 실행부도 전제를 직접 확인한다.

**② 성향이 게임플레이 RNG를 소비했다.** 흔들림을 `Math.random()`으로 뽑았더니,
시드 고정 스위트(`runImpactWoundClosureSuite`)의 탄도 판정 두 건이 깨졌다 —
유닛 생성 때 난수 2개를 더 뽑아 그 뒤 순서를 통째로 밀었기 때문이다.
지금은 **이름 해시**에서 뽑는다. 재현도 되고 순서도 안 민다.

스위치는 `USE_TRAITS` / `GAME.traitsOn`. 유닛에 `traits`를 직접 주면 그게 우선한다.

## 목표 선점 — "저건 누가 맡았다"

성향이 의도 중복을 39% → 18%까지 내렸지만, 남은 중복은 성격이 달랐다. 잡아 보니
**아군이 목표를 들고 있는 표본의 41%에서 둘 이상이 같은 문턱을 맡고 있었다.**
같은 대상을 향한 중복은 점수 편향으로 안 갈린다.

계층(분대장 AI)을 세우지 않았다. 유닛이 **선점 하나만** 들고(`unit._claim`) 행동이
바뀌면 놓는다 — 엄폐 슬롯 예약(`targetSlotId`)이 "같은 엄폐물을 둘이 잡지 않는다"를
하는 것과 같은 모양이다. 죽거나 쓰러지면 조회에서 자연히 빠져 만료 처리가 필요 없다.

> 경계: 선점은 **의도의 공유**이지 지식의 공유가 아니다. 남이 무엇을 보고 있는지는
> 여전히 각자의 믿음이고, "저 문은 누가 맡았다"만 팀이 안다 — 무전에 해당한다.

### 다른 문을 고르라는 건 답이 아니었다

처음엔 "선점 안 된 문부터 고른다"로 만들었다. **안 먹혔다** — 중복 41% → 43%.
문이 하나뿐인 방에서 넷이 그 문을 보고 있으면 폴백이 결국 같은 문을 고른다.
그리고 애초에 문이 하나면 다른 문을 고르는 게 답이 아니다. **하나가 밀고 나머지가
각을 잡는 것**이 답이다.

그래서 선점은 금지가 아니라 **표시**다. 대상이 맡혀 있으면 그 표시를 점수가 읽고
**미는 행동만**(`clearUnknownRoom` / `fragThenEnter` / `peekAndAssess`) 감점한다.
경계하는 행동은 그대로다.

### 키는 반올림이 아니라 근접이다

문턱은 유닛마다 제 이름(TH-01)을 붙이므로 이름으로는 못 맞춘다. 처음엔 24 px 격자로
반올림했는데, **자체테스트가 경계 문제를 잡았다** — 같은 문을 4 px 다르게 본 두 관측자가
`(400,300)`은 13행, `(404,297)`은 12행으로 갈렸다. 지금은 40 px 근접으로 본다.

### 측정 (30초 × 6회)

| | 성향 OFF · 선점 OFF | 성향 ON · 선점 OFF | 성향 ON · 선점 ON |
|---|---|---|---|
| 아군 의도 중복 | 39% | 33% | **13%** |
| **같은 문턱 중복** | — | **41%** | **1%** |
| 아군 `holdAngle` | 57% | 58% | **71%** |

**`holdAngle`이 올라간 건 정직하게 적는다.** 그리고 이게 다음 일을 정확히 가리킨다 —
지금 "미는 걸 그만둔 대원"이 할 수 있는 게 `holdAngle`밖에 없다. **미는 동료를
지원하는 행동이 없다.** 각을 잡는 것과 지원하는 것이 같은 행동으로 뭉뚱그려져 있고,
선점이 그 빈자리를 드러냈다.

스위치는 `USE_CLAIMS` / `GAME.claimsOn`, 감점 크기는 `GAME.claimPushPenalty`(기본 26).
감점 12에서는 중복이 18%까지만 내려간다 — 세게 잡을수록 중복은 사라지고 각 잡기는 늘어난다.

## holdAngle을 읽을 수 있게 만들고, 그 안에서 엄호를 꺼냈다

선점을 넣자 `holdAngle`이 58% → 71%로 올랐다. 그런데 **그 71%가 무슨 뜻인지 지표로
읽히지 않았다** — 대기·경계·엄호·할 일 없음이 한 행동에 다 들어가 있었기 때문이다.
그래서 먼저 분해했다(표본 2,747):

| holdAngle 시간 | 아군 | 적 |
|---|---|---|
| 총성 듣고 대기 | 46% | **82%** |
| **동료가 미는 중이라 비켜섬** | **33%** | 1% |
| 방향 경계 | 18% | 11% |
| 순수 대기 | 0% | 6% |

두 가지가 한 번에 보였다. 적의 82%는 "총성 들으면 안 움직인다"이고 그건 의도한 동작이다.
**아군의 33%는 선점이 만든 시간**인데, 그때 하는 일이 제자리에서 각 잡기뿐이라
**미는 동료가 향하는 문을 아무도 안 보고 있었다.**

### 엄호 — 겨누는 대상이 다르다

`coverMate`는 `holdAngle`과 하는 일이 비슷해 보이지만 **겨누는 대상이 다르다.**
holdAngle은 위협 방향을 보고, 엄호는 **동료가 맡은 문**을 본다. 재료는 이미 있었다 —
선점(`unit._claim`)이 "누가 무엇을 맡았는지"를 들고 있다.

| 30초 × 6회 (아군) | 엄호 OFF | 엄호 ON |
|---|---|---|
| `holdAngle` | 62% | **52% / 60%** (배치 둘) |
| `coverMate` | — | **15% / 7%** |
| 같은 문턱 중복 선점 | 0% | 0% |

정직하게 — **`holdAngle` 감소는 변동 폭 안이다.** 두 배치가 52%와 60%로 갈렸고 대조군이
62%다. 확실한 건 `coverMate`가 실제로 채택된다는 것(아군 시간의 7~15%)과,
그 시간이 **이전에는 이름조차 없던 행동**이라는 것이다.

### 이제 숫자가 스스로 말한다

`aiAction.holdKind`를 남긴다(판단에는 안 쓴다 — 기록만). 게임 안에서 직접 읽은 값:

```
아군 holdAngle 내역  gunshotWait 53% · matePushing 28% · idle 12% · watchingAngle 6%
적   holdAngle 내역  gunshotWait 63% · idle 31% · matePushing 3%
```

적의 `idle` 31%가 다음 후보다 — 방어 측이 아무 이유 없이 서 있는 시간이다.

### 자체테스트가 내 방어의 구멍을 잡았다

성향 편향은 "점수 0(=자격 없음)인 후보에는 안 붙는다"로 막아 두었는데,
**노이즈가 더해진 뒤 점수로 판정하고 있었다.** 노이즈가 0을 살짝 양수로 밀면 편향이
그대로 붙어서, 원래 막으려던 크래시 경로가 열려 있었다. 자격 판정은 이제
**노이즈 이전 점수(`raw`)**로 한다. 후보에 `raw`와 `score`를 따로 들고 다닌다.

같은 부류로, 엄호 자체테스트 셋이 처음에 **잘못된 이유로 통과**했다 —
`window.UNITS = [...]`로는 `UNITS` 바인딩이 안 바뀌어서 전부 "대상 없음"이 나온 것뿐이었다.
선점 때와 같이 roster 주입구를 달아 실제로 검사하게 고쳤다.

스위치는 `USE_SUPPORT` / `GAME.supportOn`.

## 엄호 아래 이동 — 겨누기에서 누르기로

바라보는 것은 엄호가 아니다. `coverMate`는 총구만 문쪽에 두고 **한 발도 안 쐈다.**
제압은 이미 탄착군·판단 품질·소음 감지에 다 걸려 있으니, 탄을 넣기만 하면 효과는 따라온다.

먼저 확인한 것 — **벽에 쏘는 게 제압을 만드나.** 만든다.
`applySpecialAmmoEffects`가 (1) 탄도 통과 1.19 m 안, (2) 벽·엄폐물 탄착 주변 3 m 안에
제압을 넣고, **둘 다 표적 유닛이 없어도 돈다.** 좌표 사격으로 충분했다.

> 반경을 한 번 잘못 적었다. 코드 주석의 "~1.9m"는 20px/m 시절 값이고,
> 지금 `PX_PER_M = 32`에서 `NEAR_MISS_RADIUS = 38px`는 **1.19 m**다.
> 채점 반경을 4 m로 잡았던 첫 측정이 그래서 후했다.

덤으로 **죽어 있던 의도 하나를 살렸다.** `SUPPRESSIVE_FIRE`는 산포 보정·사격호·디버그
출력에 전부 배선돼 있는데 `chooseFireIntent`가 그걸 **한 번도 반환하지 않았다.**
서술자만 하나 추가하니 생산자가 생겼다.

### 문을 겨눴더니 21발 중 0발이 사람 근처였다

첫 설계는 **동료가 맡은 문**을 눌렀다. 사후 채점 결과가 이랬다.

| | 값 |
|---|---|
| 엄호사격 | 21발 |
| 조준점 4 m 안에 살아있는 적 | **0발 (0%)** |

기하적으로 당연하다. 그 문은 **미확인** 방의 문이고, 안에 누가 있다고 믿었다면 동료는
클리어가 아니라 교전을 하고 있었을 것이다. `coverMate`는 보이는 적이 있으면 점수가 0이다.
**구조적으로 빈 방을 겨누고 있었다.** ON/OFF 두 팔에서 적 제압이 6.2 → 5.9로 안 움직인 건
잡음이 아니라 정확한 측정이었다.

대안을 재 봤다. 같은 `coverMate` 표본 184건에서:

| 조준 후보 | 표본 중 | 4 m 안에 진짜 적 |
|---|---|---|
| 동료가 맡은 **문** | 100% | **2%** |
| 엄호자 자신의 **위협 기억** | 33% 보유 | **100%** (60/60) |

믿음이 약한 게 아니라 **조준점이 틀렸던 것이다.** (섬광 때와 반대 결론인데 이유가 다르다 —
거기선 프래그 계획이 고른 *방*에 대해 믿음을 물었고, 여기선 유닛에게 *자기 위협 기억*을
물었다. 후자가 위협 기억이 원래 잘하는 일이다.)

그래서 **누를 대상을 안 믿으면 아예 안 쏜다.** 빈 문에 쏘는 건 탄약과 총성만 쓴다.

기존 견제사격(`maybeSuppressingFire`)도 `coverMate` 중에 이미 돌고 있으므로, 엄호가 더하는
것은 **조율**이다 — 확신 문턱을 0.45에서 0.35로 낮추고(동료가 지금 건너고 있다),
간격을 2.5초에서 1.7초로 줄이고, 저숙련도 통과 못 하는 사선 hard gate를 건다.

### 결과 — 기구는 끝까지 돈다

| 12회 × 35초 | 값 |
|---|---|
| 실제 발사 | 9탄 (묶음 첫 발 표본) |
| 탄도→최근접 적 수직거리 | 중앙값 **0.78 m** |
| 1.19 m(제압 반경) 안 | **67%** |
| 적 직격 | 3 (33%) |
| 적 근접제압 적용 | 3 (33%) |

**빈도는 낮다.** 12회에서 9묶음, 회당 0.75다. 기회가 죽는 곳 1위는 압도적으로
`no_belief`(4878) — 엄호자가 누를 대상을 모르는 시간이 대부분이고, 이건 튜닝이 아니라
시나리오의 성질이다.

**부작용도 정직하게.** 제압 적용 24건 중 적은 3건이고 **나머지 21건은 아군**이다.
엄호자가 자기 팀 옆을 지나 쏘기 때문이다. 피해는 없지만(아군 근접탄은 약화된다)
우리 편을 적보다 7배 더 놀래고 있다.

> **내 하네스가 한 번 거짓말했다.** "제압 적용 0건"을 보고했는데 게임이 아니라 계측 버그였다 —
> `tickCoverFire` 호출 **뒤에** 사수 표식을 달았는데 발사는 그 호출 **안에서** 끝난다.
> 표식보다 제압이 먼저 찍혀서 전부 안 세어졌다. 표식을 앞으로 옮기니 보였다.

스위치는 `USE_COVER_FIRE` / `GAME.coverFireOn`. 사후 채점 로그는 `GAME.coverFireLogOn`.

## 연막 1단계 — 사고를 먼저 막고, 그다음에 진짜를 만든다

연막을 넣기 전에 **지금 먼지가 시야에 무엇을 하는지부터** 쟀다. 그러다 아무도 못 본
과발동을 찾았다.

`sampleDustAtPoint`가 겹친 구름 밀도를 **상한 없이 합산**한다. 그래서 한 지점에 소총
8발만 쏴도 구름 25개가 쌓여 **지금도 `dust_blocked`가 난다.** 지속 사격이 우발적
연막을 만들고 있었다. "먼지 시각차단을 강화한다"는 계획대로 갔으면 이걸 같이 키웠을 것이다.

그래서 **부산물 먼지와 목적제 연막을 따로 센다.** 먼지는 `DUST_VISION_CAP`에 걸려
흐리게만 하고(탄착 8발 가시배율 0.85, 40발 0.90, **차단은 못 함**), 연막은
`obscurant: true`로 상한을 안 받는다 — 차단이 연막의 일이기 때문이다.

### "먼지 시스템을 쓴다"는 절반만 맞았다

| | 기존 먼지 한 덩이 | 연막 |
|---|---|---|
| 반경 | 0.63 m | **5 m** |
| 밀도 | 0.36 | **1.05** |
| 수명 | 2.9 초 | **26 초** |
| 10 m 사선 광학깊이 | **0.015** | 1.10 |

구조(`spawnDustCloud` · `sampleDustAlongLOS` · 벽 클리핑 · 렌더)는 그대로 쓴다.
**파라미터는 못 쓴다** — 축마다 한 자릿수씩 다르다.

### 피어오름을 한 번 틀렸다

반경/시간으로 계산한 `spreadRate`가 `updateDustClouds`의 `min(1, spreadRate*dt*0.9)`를
포화시켜서 **한 틱에 만재**가 됐다. 바로 위에 "던지자마자 벽이 서면 그건 연막이 아니다"라고
써 놓고 코드가 안 지키고 있었다. 성장식의 시정수에서 역산해 고쳤다.

| t | 반경 | 가시배율 | |
|---|---|---|---|
| 0.5초 | 2.26 m | 0.81 | |
| 1초 | 3.25 m | 0.62 | |
| 2초 | 4.33 m | 0.36 | |
| **3~15초** | 5 m | **0.20~0.27** | **차단** |
| 20초 | 5 m | 0.31 | |

**3초 피어오름 → 12초 차단 창 → 감쇠.** 그 기다림이 있어야 "던지고 기다렸다 건넌다"가
`pendingFrag` 상태기계를 그대로 재사용할 수 있다.

### 값은 2단계에 달려 있다

주입 A/B(AI 사용 코드 없이 연막만 넣음)에서 기구는 끝까지 돌았다 — `dust_blocked` 16건.
19.1 m 주입은 0건인데 사거리 측정과 정확히 맞는다.

그런데 **더 중요한 숫자가 나왔다: 적-아군 가시율 2.09%**(표본 31,076). 이 시뮬레이션에서
서로 보이는 순간 자체가 이미 희소하다 — 벽·180° 시야각·사거리가 대부분을 이미 차단한다.
심지어 t=8초에 서로 보이는 쌍이 아예 없는 회차가 **8번 중 5번**이었다.

> **무작위로 던지는 연막은 거의 무의미하다.** 손댈 수 있는 표면이 2%뿐이다.
> 값이 나오려면 사선이 **막 중요해지는 순간과 자리**여야 하고, 그게 `screenThenCross`다.
> 1단계는 건전하지만 값은 전적으로 2단계에 있다.

결과 지표는 주장하지 않는다 — 주입 성공 3/8에 차단 16건으로는 피해 차이를 가릴 수 없다.

스위치는 `USE_SMOKE` / `GAME.smokeOn`.

## 연막 차폐 후 횡단 — 꼬리만 재사용하고, 가설 다섯 개를 태웠다

`pendingFrag`를 통째로 쓰면 `approach → look → decide` 머리가 딸려 오는데, 그 긴 접근 구간이
이번 세션 내내 계획을 죽인 원인이다(프래그 중단 사유 1·2위가 접근·예산). 연막은 다르다 —
**지금 서 있는 자리에서 건널 문을 가린다.** 그래서 꼬리(`throw → wait → enter`)만 쓰고
계획을 처음부터 `throw` 단계로 만든다. 조준점도 다르다: 프래그는 방 안 4 m를 노려 사람을
때리지만, 연막은 **문턱 자체**를 덮어 그 문을 지나는 사선을 끊는다.

결과는 명확했다 — **채택 7 → 계획 7 → 투척 7, 완주율 100%.** 걸어가다 죽는 구간이 없으니
프래그가 못 하던 것을 한다.

### 소유권이 세 군데 흩어져 있었다

그런데 **차폐 성공이 0이었다.** 원인은 다단계 의도의 소유권이 세 곳에 각각 인라인
문자열 비교로 적혀 있고, 내가 그중 둘만 고친 것이었다.

| 곳 | 빠뜨렸을 때 증상 |
|---|---|
| `executeUtilityAction`의 정리 게이트 | 계획이 세워지자마자 지워진다 |
| `isActionDone` (두 표) | 행동이 즉시 완료 처리된다 |
| **`_planHeld`** (전환 판정) | 후보가 안 나와 점수 0 → 다음 재평가에서 밀려난다 |

세 번째 바로 위 주석은 **이 세션에서 내가 `fragThenEnter`를 위해 직접 쓴 것**이었다:
"던지자마자 계획이 취소된다." 그 경고를 내가 다시 밟았다. 이제 셋 다
`actionOwnsFragPlan` 하나로만 말하고, 자체테스트가 주인과 비주인을 못 박는다.

### 가설 다섯, 그중 넷이 죽고 하나는 내 검증이 틀렸다

셋을 다 고쳐도 **차폐 0**이 남았다. 진단을 붙여 하나씩 태웠다.

| 가설 | 결과 |
|---|---|
| 튕겨서 빗나갔다 | **기각** — 낙하 오차 0.0 m (전 회차) |
| 문 벽이 구름을 잘라낸다 | "기각" ← **내 검증이 무효였다** |
| enter가 NaN이라 조용히 실패 | **기각** — 실제 문턱에서 유한, span od 1.51 |
| `detonated`가 안 서서 검사가 호출 안 됨 | **기각** — 떼어내도 그대로 |
| 유닛 위치에서 재서 희석 | **참** — 14 m 선에서 od 0.26 (구름은 만재) |

클리핑 검증이 무효였던 이유: 벤치에서 스폰과 샘플 사이에 **렌더가 안 돌아 `clipRadii`가
계산되지 않았다.** 클립이 비활성인 상태로 켬/끔을 비교해 놓고 "동일하니 원인 아님"이라고 읽었다.
**유일하게 맞는 가설을 망가진 테스트로 지웠다.**

진짜 원인은 그것과 같은 것이었다. 내 검사는 **문 폭 방향으로 4 m**를 쟀는데 문은 1 m 남짓이라
나머지 3 m가 **벽 속**이고, 거기서 `radial_wall`이 연막을 정확히 0으로 만든다. 구름은
내내 만재(4.9 m·밀도 1.00)로 조준점에 앉아 있었고, 내가 벽 내부를 적분하고 있었다.

이제 **문을 통과하는 방향**으로 8 m를 잰다. 거기가 열린 공간이고, 구름이 자라야만 덮이므로
기다릴 이유도 거기서 생긴다. (3 m 토막으로 재는 안은 자체테스트가 기각했다 — 작은 구름도
바로 덮여서 대기가 사라진다.)

| | 값 |
|---|---|
| 채택 · 계획 · 투척 | 7 · 7 · 7 |
| **차폐 성공** | **6 / 7** |
| 안 피어서 그냥 건넘 | **0** |

> **값은 아직 실증되지 않았다.** 아군 피해 118 · 생존 2.83으로 기준선(67~102 · 3.0~3.4)보다
> 오히려 나쁘고, 6회로는 가릴 수 없다. 그리고 **차폐 중 피해가 초당 3.16으로 미는 중(3.00)과
> 다르지 않다** — 연막은 문을 가리지 던지는 사람을 가리지 않는데, 유닛은 구름이 자라는
> 2~3초를 **자기가 서 있던 자리에서** 기다린다. 그 자리가 노출돼 있으면 기다림이 비싸다.
> 종료 사유도 `switched_to_seekCover` 4건 — 기다리다 맞아서 엄폐로 갈아탄다.

스위치는 `USE_SMOKE` / `GAME.smokeOn`. 계획 진단은 `GAME._fragLog`의 `reason === 'screen'`.

### 던지고 빠진다 — 접근 다리를 없앤 자리에 대기 노출이 들어왔다

접근 다리를 뺀 판단은 옳았다(완주율 100%). 그런데 노출이 사라진 게 아니라 **대기로 옮겨갔다.**
차폐 중 피해가 초당 3.16으로 미는 중(3.00)과 다르지 않았고, 계획 종료 사유 1위가
`switched_to_seekCover` — 기다리다 맞아서 엄폐로 갈아탄 것이다. **연막은 문을 가리지
던지는 사람을 가리지 않는다.**

그래서 던진 뒤 물러섰다가 연막이 서면 나온다. 프래그 대기는 이동 명령을 취소하므로
(문 옆에서 가만히 기다리는 게 프래그의 일이다) 연막만 그 취소에서 뺐다.

**첫 판은 통째로 불발이었다 — 물러섬 0/4.** 계기를 달아 보니 이유가 이랬다:

| 시도 | 결과 |
|---|---|
| 뒤로 2.8 m | **전량 무효** (벽) |
| 뒤로 1.2 m | 4번 중 3번 무효 |

뒤로 **직선으로** 물러서니 벽에 박힌다. 전술적으로도 틀렸다 — 문 앞에서 빠지는 건
뒤로 걷는 게 아니라 **문설주 뒤 옆으로 붙는 것**이다. 부채꼴 7방향 × 3거리를 훑고
**문턱이 안 보이는 자리**를 우선하도록 바꿨다.

| | 물러섬 전 | 직선 물러서기 | 부채꼴 |
|---|---|---|---|
| 물러섬 성공 | — | **0 / 4** | **6 / 6** (문설주 뒤 3건) |
| **차폐 중 피해(초당)** | **3.16** | 2.14 | **2.12** |

물러선 대가도 측정에 잡혔다 — `enter_timeout` 2건. 2.8 m 물러섰으니 건널 거리가 늘었는데
제한시간이 그대로였다. 물러선 거리를 시간으로 환산해 돌려줬다.

### 경로 비용에 연막 항

`dangerCostAt`이 연막 밀도만큼 위험을 **깎는다**(최대 0.30배). 더하지 않는다 —
연막은 새 위험을 만들지 않는다. **부산물 먼지는 안 친다**: 가려 주는 건 연막이고,
탄착 먼지에 할인을 주면 *벽에 대고 쏘면 그 앞 땅이 안전해지는* 꼴이 된다.

이 항이 없으면 경로가 연막을 선호할 이유가 없고, 깔때기 비용에서 겪은
"경로는 바꿨는데 결과가 안 바뀐다"를 그대로 반복하게 된다.

스위치는 `USE_SMOKE_PATH` / `GAME.smokePathOn`.

> **결과는 여전히 주장하지 않는다.** 아군 생존 3.17 · 피해 109로 물러서기 전(2.83 · 121)보다
> 낫지만 6회로는 가를 수 없다. 확실한 것은 **차폐 중 피해가 3.16 → 2.12로 두 번의 측정에서
> 같은 방향으로 움직였다**는 것과, 고리가 끝까지 돈다는 것이다.

## 방어 측 반응 — 경보를 울렸더니 방어자가 굳었다

이게 없으면 연막은 공격자 전용 치트다. 눈이 가려진 방어자가 수동적이 되는 게 아니라,
**자기 문 앞에 연막이 피었다는 사실 자체가 정보**여야 한다.

**새 유틸리티 행동은 만들지 않았다.** 이번 세션에서 행동을 더하거나 가격을 바꿀 때마다
배분이 귀속 불가하게 흔들렸다(`guardEntry` 32→18→56→49→37, `reposition` 7→31→14).
방어자에겐 이미 `guardEntry`가 돌고 그건 `beyondRoomDanger`가 몰아주므로, **믿음만 바꿨다** —
보이는 연막이 아는 문턱 근처면 그 문 너머를 뜨겁다고 믿는다. 투시는 금지고, 자체테스트가
`isLOSBlockedForBlast`를 강제로 막아 경보가 안 오르는 것을 못 박는다.

### 서 있는 행동에 알람을 걸면 서 있게 된다

스위치는 작동했다(경보 221 대 0). 그런데 방어자가 **더 얌전해졌다.**

| 적 행동 | 경보 ON | 경보 OFF |
|---|---|---|
| `guardEntry` | **50%** | 35% |
| `repositionToCorner` | 13% | 22% |
| `engageEnemy` | **사라짐** | 5% |
| `clearUnknownRoom` | **사라짐** | 3% |

원인은 내 배선이다. 알람을 `guardEntry`로 보냈는데 **`guardEntry`는 서서 보는 행동**이라,
경보가 "더 위험해져라"가 아니라 "가만히 더 열심히 봐라"가 됐다. 교리도 반대다 —
내 문에 연막이 피면 **그 안으로 쏠 준비를 하는 것**이지 쳐다보는 게 아니다.

그래서 경보받은 방어자가 그 문을 **좌표 사격**으로 누른다. 엄호사격이 만들어 둔 기계를
그대로 쓰되 두 게이트가 다르다: **움직이는 동료를 요구하지 않고**(연막이 신호다),
**위협 기억도 요구하지 않는다**(연막이 근거다). 사선 hard gate와 탄약 예비는 그대로다.

| 적 행동 | 경보 ON (사격) | 경보 OFF |
|---|---|---|
| `guardEntry` | **29%** | 45% |
| `engageEnemy` | **9%** | 2% |
| 경보 사격 | **9회** | 0 |

수동성은 고쳐졌다.

### 물러서기가 경보를 이기는 것으로 보인다

그런데 **두 번의 A/B에서 연속으로 공격 측이 더 좋아졌다**(아군 피해 41 대 133,
생존 3.67 대 2.67). 설계 의도와 반대다.

기전이 그럴듯하다: 공격자는 던지고 **문설주 뒤로 빠진다**. 방어자는 연막을 정확히
신호로 읽고 그 문으로 쏘는데 — **거기엔 아무도 없다.** 연막이 방어자의 사격을
빈 문간으로 끌어내는 셈이다.

> 사실이면 버그가 아니라 진짜 전술적 상호작용이다. 다만 **6회로는 주장할 수 없다.**
> 방향이 두 번 일치한다는 것과 기전이 설명된다는 것까지가 지금 말할 수 있는 전부다.
> 다음에 확인할 것: 경보 사격을 **누가 실제로 나올 때까지** 아끼면 방향이 뒤집히는가.

스위치는 `USE_SMOKE_ALERT` / `GAME.smokeAlertOn`.

## 왜 결과 지표가 한 번도 안 갈렸나 — 자를 먼저 재다

이번 세션의 거의 모든 기능이 "표본 6회로는 못 가른다"에서 멈췄다. 맵을 바꾸기 전에
원인을 쟀더니 **내 가정 둘이 틀렸다.**

**접촉은 드물지 않다.** 첫 접촉 평균 0.4초, 접촉 없던 회차 0, 첫 피해 3.5초,
무언가가 보이는 시간이 38%. 강제 접촉이나 목표를 만들 이유가 없었다.
(앞서 인용한 "가시율 2.09%"는 오해를 부르는 수다 — 아군 4 × 적 10 = 40쌍 전부의 평균이라
대부분 멀리 있는 쌍이다.)

**진범은 지표였다.**

```
아군피해  [100, 81, 100, 117, 100, 142, 104, 100, 0, 227]
아군생존  [3, 3, 3, 3, 3, 3, 3, 3, 4, 2]
```

100이 네 번, 생존이 10번 중 8번 정확히 3. **아군 피해는 연속량이 아니라 "몇 명 쓰러졌나"의
프록시**이고, hp 100짜리 유닛이 죽으면 100이 통째로 찍힌다. 나는 양자화된 지표를
6회 표본으로 읽고 있었다.

### 자를 바꿔도 안 됐다

| 지표 | 변동계수 | 20% 차이 검출에 팔당 |
|---|---|---|
| 아군 생존 | 0.25 | 24회 |
| 아군 노출 시간 | 0.29 | 33회 |
| 교전 시간 | 0.42 | 69회 |
| 아군 발사 탄수 | 0.56 | 123회 |
| 적 피격 횟수 | 0.61 | 145회 |
| **아군 피격 횟수** | **0.76** | 227회 |
| **아군 피해(그동안 쓴 것)** | **0.77** | 234회 |

**"연속량이면 변동이 낮을 것"이라는 내 가설은 틀렸다** — 피격 횟수가 피해만큼 나쁘다.
그리고 같은 지표를 앞서 0.49로, 여기서 0.77로 쟀다. **분산 추정 자체가 12회로는 안 안정된다.**

변동이 어디 있는지는 회차 목록에 그대로 보인다 — `피격 0·교전 3초` 대 `피격 27·교전 22초`.
**교전 결과가 아니라 교전량이 흔들린다.**

### 공격 측에 추진력이 아예 없었다

원인을 찾았다. 아군 행동에 `holdAngle`·`engageEnemy`·`coverMate`·`seekCover`·
`repositionToCorner`는 있는데 **전진하는 행동이 하나도 없다.** `clearUnknownRoom`은 적 전용,
`fragThenEnter`·`screenThenCross`는 위험 근거가 있을 때만. 평소엔 플레이어가 명령하지만
하네스엔 플레이어가 없어서, 아군이 하는 일이 전부 반응에서 창발한다.

그래서 맵에 목표(현관 → 금고실)를 두고 `advanceToObjective`를 만들었다.
**성공 기준을 미리 못 박았다** — 노출·생존 변동계수가 0.29/0.25보다 내려갈 것.

### 실패했다 (`USE_OBJECTIVE = false`)

| | 목표 없음 | 목표 35초 | 목표 70초 |
|---|---|---|---|
| **목표 도달 회차** | — | **0 / 12** | **0 / 10** |
| 전진 채택 | — | 79 | 94 |
| 노출 CV | 0.29 | 0.47 | 0.46 |
| 생존 CV | 0.25 | 0.19 | 0.29 |
| 아군 생존 · 피해 | 3.0 · 107 | 3.4 · 70 | **2.7 · 143** |

기준 양쪽 다 실패다. 실행 시간 탓도 아니었다 — 70초로 늘려도 **0/10**이고, 오히려 아군이
더 죽는다.

> **순진한 전진은 도착하지 못하고 죽는다.** 이건 실패지만 값이 있는 실패다:
> 공격 측에 추진력을 주려면 걷게 하는 것으로 부족하고, **도약 전진·엄호 아래 이동이
> 실제로 작동해야** 한다 — 이번 세션이 내내 만들었지만 아직 값을 실증하지 못한 그것들이다.
> 코드와 테스트는 남긴다(깔때기 비용과 같은 처리).

스위치는 `USE_OBJECTIVE` / `GAME.objectiveOn`.

### 이 세션에서 내 하네스가 게임보다 자주 틀렸다

셋 다 "0이 나왔다"는 형태였고 셋 다 계측 버그였다.

| 보고한 값 | 실제 원인 |
|---|---|
| 엄호사격 제압 **0건** | 사수 표식을 호출 **뒤**에 달았는데 발사는 그 안에서 끝난다 |
| 먼지 광학깊이 **0** | 갓 생성된 구름은 `visualAlpha` 0 (0.25초 페이드인) — 샘플러가 건너뛴다 |
| 연막 차단 **0건** | `_checkVisibilityBase`를 직접 불러 **먼지 래퍼를 건너뛰었다** |
| 클리핑 **무관** | 스폰과 샘플 사이에 렌더가 안 돌아 `clipRadii` 미계산 — 꺼진 클립끼리 비교했다 |

0이 나오면 게임보다 계측을 먼저 의심하는 게 맞다.

## 이동사격 — 공짜와 불가능 사이에 아무것도 없었다

"이동사격 퍼짐을 대폭 줄이자"는 요청으로 열었는데, **줄일 페널티가 애초에 걸려 있지
않았다.** 명중률과 퍼짐 양쪽에 같은 조건이 붙어 있었다:

```js
if (shooter.movePath && shooter.movePath.length > 0 && !shooter.currentTarget)
```

`currentTarget`이 있으면 페널티가 통째로 빠진다. 실측(m4a1 · 중하중 · 8 m 표적):

| 상태 | 명중률 | 퍼짐 |
|---|---|---|
| 정지 · 표적 있음 | 0.759 | 0.49° |
| **이동 · 표적 있음** | **0.759** | **0.49°** ← 페널티 0 |
| 이동 · 표적 없음 | 0.417 | 1.17° ← 명중 55% · 퍼짐 2.39배 |

**달리면서 조준하고 쏘는 게 서서 쏘는 것과 완전히 같았고**, 겨눌 대상이 없으면 갑자기
가혹해졌다. 요청한 "정지보다 나쁘되 할 만한" 중간이 어느 쪽에도 없다.

### 게이트를 없애고 크기를 낮췄다

두 가지를 같이 했다. 이동이면 표적 유무와 무관하게 **항상 대가**를 물리고(게이트 제거),
그 대가를 대폭 낮춘다(요청). 판정은 `isFiringOnTheMove` 한 곳에서만 한다 — 명중률과
퍼짐이 서로 다른 조건을 보고 갈리는 게 애초의 사고였다.

퍼짐은 무기별 배수(1.35~3.0)를 **평평한 상수로 갈아치우지 않고 1 쪽으로 압축**한다.
`1 + (m − 1) × 0.30`. 기관총이 권총보다 이동 중 나쁘다는 순서가 남는다.

| 상태 | 명중률 | 퍼짐 |
|---|---|---|
| 정지 | 0.759 | 0.49° |
| **이동 (표적 유무 무관)** | **0.645** | **0.73°** |
| | 명중 85% | 퍼짐 1.49배 |

> **정직하게 말하면 이건 한쪽을 깎는다.** 조준 이동사격은 지금까지 공짜였고 이제
> 약간 불리하다. 비조준 이동사격은 크게 좋아진다. 요청은 후자였지만, 전자를 그대로 두면
> "이동사격에 대가가 있다"가 성립하지 않는다.

### 소비되는가 — 죽은 코드가 아니다

벤치에서 숫자가 바뀐 것과 게임이 그 숫자를 쓰는 것은 다르다. 코드 주석은
"friend는 교전 시작 시 이동 중단"이라고 적혀 있어서, 사실이면 이 재조정은 대부분
죽은 코드다. 6회 × 35초 실측:

| | 총 발사 | 이동 중 | 그중 표적 있음 |
|---|---|---|---|
| 아군 | 91 | **31 (34%)** | **31 / 31** |
| 적 | 82 | **25 (31%)** | 24 / 25 |

**전체 사격의 3분의 1이 이동 중이고, 그 거의 전부가 표적을 잡은 상태** — 정확히 지금까지
페널티가 0이던 경우다. 주석이 말한 "교전 시 이동 중단"은 실제 동작이 아니었다.

명중률은 실전에서 갈리지 않는다(ON 80.6% 대 OFF 87.5%, 아군 이동 사격 n≈30).
방향은 맞지만 이 세션이 이미 못 박은 대로 **팔당 25~30회 없이는 주장하지 않는다.**
게다가 이동 사격은 가까운 거리에서 더 자주 일어나 교란까지 섞여 있다. 값의 근거는
결정적인 벤치 쪽이고, 실전 측정의 역할은 **"소비되는가"까지**다.

스위치는 `USE_MOVING_FIRE` / `GAME.movingFireOn`. 끄면 옛 게이트와 옛 값(0.55 · 무기 배수
그대로)이 정확히 돌아온다 — 자체테스트가 그걸 고정한다.

## 방어자는 둘러본다 — 그리고 점수판이 흔들렸다

적 `holdAngle`의 `idle`을 건드리려고 열었더니 **규모부터 틀렸다.** 31%는
`holdAngle` 안에서의 비중이고, 적 **전체** 시간으로는 13%다. 그리고 `guardEntry`는
32%로 멀쩡히 채택되고 있었다 — 방어 행동이 죽은 게 아니었다.

`idle`의 정의도 내가 잘못 말했다. `preferredWatchAngle`이 null이라고 썼는데,
실행부를 보면 `ang`은 `lastHeardGunshot`과 `ctx.threatPos`에서만 나온다 —
`holdAngle`은 `preferredWatchAngle`을 **아예 읽지 않는다.**

### 안 돌아본 방어자는 자기 방을 모른다

| idle인 적 | 값 |
|---|---|
| 아는 문턱 0개 | **56%** |
| 방 안에 서 있음 | 100% |
| 한 번도 안 움직임 | 60% |
| **시야 닫힘(다 봤다)** | **0%** |

마지막 줄이 원인이다. 이들은 "다 봐서 볼 게 없는" 게 아니라 **아직 안 본 방 안에
가만히 서 있다.** `viewArc`는 180°이고 `senseFor`는 `unit.facing` 중심 부채꼴만 훑는다.
한 번 안 돌면 등 뒤 벽을 영원히 모르고, 그 벽의 문턱도 모른다. 그래서 `guardEntry`가
경계할 대상을 못 찾는다. **고칠 것은 13%가 아니라 32%의 입력이었다.**

프론티어(`S.sector.openings`)가 정확히 "아직 시선이 빠져나가는 방향" = 안 본 쪽이고,
0으로 수렴하면 `sightClosed`다 — 종료 조건이 공짜다. 각도만 써 주면 된다:
본체 facing 사슬의 마지막 단계가 `preferredWatchAngle`을 이미 소비한다.
`_holdFacing`도 풀어야 했다 — 마지막 도착 시선을 영원히 붙들고 있는 게 얼어붙은 나머지 절반이었다.

| | OFF | ON |
|---|---|---|
| 스캔 중 `aimType` | — | **watch 75%** |
| 누적 회전량/유닛 | 5.5 rad | 6.8 rad |
| 관측 표면/유닛 | 15.2 | 15.9 |
| 아는 코너/유닛 | 4.09 | 4.43 |
| **확정 문턱/유닛** | **0.99** | **1.14** |

> 처음엔 "중앙값 1 → 1, 안 움직였다"고 읽었다. **중앙값이 평균 변화를 가린 것**이었다.

### 스캔이 holdAngle에게 뇌물을 줬다

첫 판에서 `guardEntry`가 32% → 25%로 밀렸다. 원인은 내 쪽이었다 —
`scoreHoldAngle`은 감시각이 있으면 **+8**을 주는데 그건 "볼 이유가 있다"는 뜻이었고,
둘러보기가 바로 그 칸을 채운다. **holdAngle이 자기 자신에게 값을 치르고 있었다.**
출처를 표시해 막았다(`_watchFromIdleScan`).

그런데 뇌물을 걷어내니 그 9%p를 `guardEntry`가 아니라 `repositionToCorner`가
가져갔다(7% → **31%**). 읽어 보니 당연했다 — reposition은 전술적 문간 코너에서
**~70점**까지 가는데 조용할 때 `guardEntry`는 상한이 ~41이다. 애초에 경쟁이 안 된다.
게다가 **둘은 같은 자리를 원한다**(reposition도 `doorway`에 +20). 하나는 문을 서서
지키고 하나는 문 옆 코너로 걸어간다.

### 가격을 두 번 틀렸다

`guardEntry`에 +20을 줬더니 **스캔이 꺼진 팔에서도** 32% → 56%가 됐다.
되돌리려던 걸 두 배로 만든 셈이라, 넓게 걸리는 항(엄폐 중 + 미노출 — 방어자에겐 거의 항상 참)을
빼고 확정 문턱 +10만 남겼다.

| 구성 | `guardEntry` | `reposition` | `idle` | `holdAngle` |
|---|---|---|---|---|
| 원래 기준선 | 32% | 7% | 13% | 53% |
| 스캔 O · 가격 +0 | 18% | **31%** | 8% | 44% |
| **스캔 O · 가격 +10 (출하)** | **37%** | 14% | **9%** | 43% |
| 스캔 X · 가격 +10 | 49% | 7% | 12% | 38% |

출하 구성은 기준선 대비 `guardEntry`가 오히려 **올랐고**(32→37), `idle`이 13→9,
뭉뚱그려진 `holdAngle`이 53→43으로 줄었다. **대가는 `reposition`이 두 배**가 된 것이다 —
코너를 더 알수록 더 옮겨 다닌다.

> **결과는 개선으로 주장하지 않는다.** 적 생존 8.40 대 8.20, 적 피해 160 대 185인데
> **아군도 같이 좋아졌다**(생존 3.20 대 3.00, 피해 80 대 101). 양쪽이 다 나아진 건
> 교전이 덜 치열해졌다는 뜻이지 방어가 나아졌다는 증거가 아니다. 5회로는 가를 수 없다.

스위치는 `USE_IDLE_SCAN` / `GAME.idleScanOn`.

## 섬광 — 몸이 아니라 감각을 때린다

프래그가 몸을 때린다면 섬광(`grenade_m84`, `type:'flash'`)은 **감각**을 때린다.
파편이 없다 — `blastRadius*`를 아예 두지 않은 것이 그 사실의 표현이다.

세기가 거리만으로 정해지지 않는 것이 요점이다:

| | 근거 |
|---|---|
| 벽 뒤면 **실명 0**, 청각은 남는다 | 빛은 모퉁이를 안 돌지만 소리는 조금 돈다 |
| 그쪽을 보고 있었으면 훨씬 심하다 | 등져도 0은 아니다(주변시·반사광) |
| 훈련된 대원은 덜 당한다 | `getReactionProfile`의 감지 배수를 그대로 쓴다 |

주입 측정 (M84, 2 m 앞에서 폭발):

| | 값 |
|---|---|
| 정면 실명 / 등짐 실명 | **3.1초 / 1.1초** |
| 청각 상실 | 4.3초 (방향 무관) |
| 반경(8 m) 밖 | 효과 없음 |

### 소비처 넷 — 마지막 하나가 새롭다

| 무엇이 | 어떻게 |
|---|---|
| `_checkVisibilityBase` | 관측자가 눈멀면 즉시 `flash_blinded` — 먼지는 **경로**를 가리지만 이건 **관측자**를 가린다 |
| `pHear` (소음 지각) | 이명 중에는 감지 확률 ×0.12 |
| `computeAimQuality` | 조준 품질 1.0 → **0.15** |
| **`tickSpatialPerception`** | **지형 학습이 멈춘다** |

마지막 것이 이 프로젝트에서 처음 있는 일이다. 지금까지 믿음이 낡는 이유는 **시간**뿐이었다.
섬광은 **남이 내 믿음을 낡게 만드는** 첫 수단이다 — 기억은 그대로 두고 갱신만 멈추므로,
눈이 멀린 유닛은 **낡은 지도를 들고 움직인다.** 그게 정확히 섬광의 값이다.

> 스캔 스킵 카운터는 **간격 검사 뒤에** 둔다. 앞에 두면 프레임 수를 세게 되어
> 3초에 216이 나왔다(실제로 건너뛴 스캔은 49).

스위치는 `USE_FLASHBANG` / `GAME.flashbangOn`.

### AI가 쓴다 — 계획은 그대로, 다른 건 둘뿐

`pendingFrag`가 `kind`를 하나 들고 다니게 했다. 계획 자체(`접근 → 피킹 → 판단 → 투척 →
대기 → 진입`)는 그대로고, 프래그와 갈리는 건 **딱 둘**이다:

| | 프래그 | 섬광 |
|---|---|---|
| 진입 짬 | 폭발 후 0.6초 (파편이 가라앉는다) | **즉시** — 눈먼 창이 짧고, 기다리면 닫힌다 |
| 안전 | 폭압 위해 (자기 0.15 / 아군 0.25) | **실명 시간** (자기 0.8초 / 아군 1.2초) |

그리고 **들어갈 방에는 섬광이 먼저다.** 프래그로 방을 여는 건 특수한 경우고, CQB 진입의
표준은 섬광이다. 섬광이 없을 때만 프래그로 떨어진다 — 실측에서 계획 15건이 전부 섬광을 골랐다.

`checkThrowSafety`가 섬광을 **실명으로** 재게 된 것이 중요하다. 폭압만 재면 섬광의 폭압은
0이므로 **언제나 "안전"**이라고 답했다. 이제 자기·아군 실명 시간을 본다. 문설주 뒤에 서면
LOS가 끊겨 실명이 0이므로, **스택업 자세가 곧 안전 조건**이 된다.

측정 (30~40초 × 8회): 아군 실명 **0회**, 갇힘 0, 완주한 계획은 투척→진입 100%.

### 조준점을 고치려다 조준점이 문제가 아님을 알았다

"고정 4 m 깊이가 아니라 믿는 적 위치를 조준하자"가 다음 개선이라고 적었는데,
**측정이 그걸 뒤집었다.** 투척 시점의 조준점을 정답(그 방 최근접 적)과 대조한 결과(표본 13):

| 후보 조준점 → 최근접 적 (중앙) | |
|---|---|
| **고정 4 m (현재)** | **2.7 m** |
| 방 중심 | 4.1 m |
| 믿는 최선 | 3.9 m |

고정 조준점이 셋 중 가장 낫다. 그리고 **믿음이 그 방에 적을 갖고 있던 건 13번 중 1번**뿐이다 —
`lastSeenEnemy` 자리가 하나뿐이라 대개 "나를 쏜 놈"이 들어 있고 그놈은 다른 방에 있다.
처음에 본 "7.5 m"는 표본 6개의 잡음이었다.

진짜 문제는 조준이 아니라 **표적 선택**이었다. **투척의 62~69%가 아무도 없는 방으로 간다.**

### 방 위험의 나이가 점유를 예측한다

954표본에서 신호가 뚜렷하다 — "그 방에 적이 실제로 있나":

| 위험 기록 나이 | | 위험 수준 | |
|---|---|---|---|
| 0~2초 | **97%** | 0.5~3 | 29% |
| 2~5초 | 80% | 3~7 | 50% |
| 5~10초 | 66% | 7~11 | 68% |
| 10~20초 | 44% | 11+ | **89%** |
| 20초+ | **28%** | | |

기존 게이트는 `danger > 0.5` + TTL 25초라 **28%짜리와 29%짜리를 다 통과시켰다.**
이제 둘을 조인다 — 계획은 5초 이내 기록으로만 출발하고(`FRAG_PLAN_FRESH`),
걸어온 뒤 10초를 넘겼으면 **던지기 직전에 접는다**(`FRAG_THROW_FRESH`).
수준도 3.0 미만은 받지 않는다. 피킹으로 직접 봤으면 나이를 묻지 않는다 — 그게 가장 새 정보다.

> **아직 효과가 안 보인다.** 빈 방 비율 69% → 62%는 표본 8개라 잡음 안이고,
> `stale_after_walk` 중단은 **0회**다 — 계획이 그 전에 예산으로 죽기 때문이다(19건 중 11건).
> 게이트 자체는 954표본이 뒷받침하지만, 그게 결과로 나타나려면 계획이 먼저 완주해야 한다.

### 값이 나오려면 사람 근처에 떨어져야 한다

기계는 확인했다. 적이 있는 방 한가운데에 직접 넣으면 LOS가 열린 적은 실명 0.7초·이명 1.4초,
벽 뒤 적은 0, 그리고 **스캔 스킵 26** — 지형 학습이 실제로 멈췄다.

그런데 그 0.7초가 작다. 2 m에서는 3.1초인데 6 m에서 0.7초다(반경 8 m 선형 감쇠).
**AI가 조준하는 곳이 문턱에서 고정 4 m 깊이이지 사람이 있다고 믿는 자리가 아니기 때문이다.**
믿는 적 위치(`lastSeenEnemy` / 방 위험)로 조준점을 옮기는 것이 다음 개선이다.

채택률은 프래그와 마찬가지로 낮다 — 4회 배치에서 투척 2회, 다른 4회 배치에서 0회.
같은 이유다(§프래그 후 진입: 던질 자리로 걸어가는 동안 총에 맞는다).

### 믿음 위상은 왜 보류인가 (`USE_BELIEF_TOPOLOGY = false`)

방과 문은 flood fill로 나온다. 그건 **닫힌 기하**가 있어야 성립하는데, 관측으로
재구성한 지형은 조각이다.

20초 실측: 한 유닛이 믿는 벽은 맵 면적의 **1.9%**(정답 7.2%), 조각 **13개**.
98%가 빈 공간으로 이어지니 flood fill은 **방 하나**를 낸다. 방이 안 나뉘면 문이
나눌 경계도 없어서, AI가 이미 찾아 둔 개구부(UNK)를 주입해도 portal은 0개다.

켜도 에러는 안 난다. 대신 조용히 능력이 준다 — `currentRegionId`가 늘 같은 방이 되고
포탈 위험 평가가 통째로 빈다. 그래서 껐고, 모든 소비자가 정답 그래프로 떨어진다.

남겨 둔 발판: `believedMapOf` / `beliefGraphOf`(리비전 게이트 + 예산 캐시),
`tacticalGraphFor`(그래프를 묻는 단일 창구), `buildTacticalSpatialGraph`의
`extraOpenings` 훅(원래 `options`를 받기만 하고 안 쓰고 있었다).

다음 시도는 **조각난 믿음에 맞는 다른 위상 모델**이 필요하다. 프로토타입처럼 방 분할을
포기하고 개구부와 "그 너머 미확인"만으로 가는 쪽이 유력하다.

> 곁가지로 살아남은 수정 둘: `portalDangers`가 위치·방향 양자화 키를 쓰게 되어
> 그래프를 다시 세워도 학습된 문 위험도가 살아남는다. 그리고 그래프 자체가 곧 관측
> 기록인 경우 `resolveSoundArrivalPortal`/`getEffectivePortalDanger`가 별도의
> "이 문을 봤는가" 기록을 요구하지 않는다.
