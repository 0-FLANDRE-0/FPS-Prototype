## 0. 다른 AI에게 한 번에 설명

현 3D판은 이미 **실제 탄착 좌표 → 5mm 단위 wound channel → 영구·일시 공동/파편/골편 → 장기·혈관·뼈 손상 → 출혈원/혈역학·의식·시야**까지 연결돼 있다. 의료탭을 만든다고 총상·장기·혈관 피해 공식을 새로 설계하지 말 것. 해야 할 것은 **기존 신체/상처 데이터의 읽기 전용 UI 투영**, **기존 인벤토리 상호작용을 장비별 수납과 이동식 IFAK 창으로 확장**, 그리고 나중에 **실물 의료 아이템 → 적절한 처치 대상 → 실제 출혈원/생리 상태**를 연결하는 일이다. 인벤토리/의료는 공통 3열 화면이며, 왼쪽·중앙·오른쪽의 의미는 UX 문서 A를 따른다. 치료 환자와 아이템 소유자는 독립적인 상태다.

### 2-1. 조직별 공동효과는 이미 차등 계산됨 — 새 배율 만들지 말 것

`wound-channel.js`의 내부 조직 효과는 아래 요소를 별도 저장한다.

```js
// 실제 소스의 구조를 설명하는 발췌/요약. 신규 처치 로직이 아니다.
effectiveVolumeM3 = permanentVolumeM3
  + fragmentVolumeM3
  + boneSecondaryFragmentVolumeM3
  + coefficient * temporaryVolumeM3;
```

- `direct`: 실제 내부 표적과 탄자 경로의 점유 구간 교차 여부.
- `effectiveVolumeM3`: 조직별 공동 민감도(`coefficient`)로 감쇠된 유효 손상 부피.
- **[코드 확인]** `medical-v2.js`의 S1 어댑터는 `vesselContusionsOnly:true`.
- **[코드 확인]** `medical-b1.js`에서는 `kind==='vessel' && !direct`를 `vesselContusions`에 기록하고 `physiologyApplied:false`로 둔다. 직접 출혈원은 `direct && permanentVolumeM3>0` 혈관만 등록.
- **예외적 구분:** 공동효과로 손상된 **실질 장기**는 유효 손상량으로 장기 출혈원을 만들 수 있으므로 '공동손상은 출혈 0'으로 일반화하면 안 됨.

### 2-2. 출혈원 구조: `bleedSources`가 치료 연결의 핵심

`medical-b1.js`의 출혈원은 다음 필드를 실제로 갖는다.

```js
// 실제 필드의 축약된 열거. 신규 데이터 스키마 제안이 아님.
{
  id, vesselName, vesselKind, injuryType,
  destination, controlClass, position,
  flowMlPerS, cumulativeMl, controlFactor,
  lesions: [], woundIds: [],
  orificeAreaMm2, majorNamed, evidence
}
```

- `destination`: `external`, `thoracic_left`, `thoracic_right`, `peritoneal`, `retroperitoneal`, `limb_compartment`.
- `controlClass`: `limb_compressible`, `junctional`, `intra_abdominal`, `intra_thoracic`, `none`.
- `position`: `partKey`, `bone`, `boneLocalPoint`, `bindActorPoint`, `actorLocalPoint`, `proximalPoint` 등. 근위 기준은 월드 Y가 아닌 해부학적 체인 순서라는 주석이 있음.
- `s.woundIds[]` ↔ `w.bleedSourceIds[]`로 상처/출혈원 연결; 같은 혈관의 다중 상처는 `s.lesions[]`.
- `bloodPoolsMl[destination]`에 실제 유출량이 합산되고, 전신 `bloodMl` 감소·`hemodynamics` 갱신으로 이어짐.

**처치 구현 시 주의할 실제 코드:**

```js
// medical-b1.js / updateBleedingB1() 내부: v56 현재 상태
s.controlFactor = 1; // reserved attachment point; no B1 treatments
```

따라서 의료 버튼에서 `controlFactor=0.2`처럼 **한 번만 대입하면 다음 틱 원복된다**. 지속되는 처치 상태를 별도로 관리하고, 매 틱 산출된 계수를 B1에 반영하는 계약이 필요하다. **[설계 제안]** 지속 처치 상태를 `appliedTreatments` 같은 구조로 보존하고 B1에서 읽도록 연결하되, 실제 타입/함수명은 구현 전 설계 확정. 기존 출혈 공식 자체를 통째로 교체하지 않는다.

**추가 검토:** `destination==='limb_compartment'`는 B1의 외부/내부 합산상 `internal`로 분류된다. 의료탭의 '눈에 보이는 외부 출혈'로 무조건 노출하거나, 반대로 임상적으로 중요한 사지 혈관 손상을 아예 UI에서 숨기지 말고 **원본 모델의 실제 의미를 확인 후 관찰 표현을 정의**해야 한다.

### 2-3. 흉강과 복강: 별도 축적 상태가 이미 있다

- `m.chestCompartments.left/right`: `chestWallOpen`, `tensionAir`, `pneumothoraxProgress`, `hemothoraxMl`, `lungEfficiency` 등.
- `m.bloodPoolsMl`: `thoracic_left/right`와 `peritoneal/retroperitoneal` 별 축적.
- `applyHemothoraxB1()`가 혈흉 축적에 따른 폐 효율 변화를 계산.
- **[설계 제안]** 흉부 씰·바늘 감압·복부 대응 장비는 각기 **공기 유입/압력/출혈원 제어** 중 무엇을 바꾸는지 명확히 분리. 흉부 씰이 혈흉 자체를 없애는 등의 범위 오류 금지.
- **[사용자 방향]** 복부 총상은 일부 대응 가능하게 하되 완치 불가, 흉강 내부 출혈은 현장에서 완전 치료 불가. 복부 지혈 폼 등 일부 기술은 현실과 차이가 있는 게임 허용 가능성으로 분류; 실제 효과 수치는 미정.

## 3. 2D 원본 의료 UI/처치에서 참고할 것 (복사와 재구현을 구분)

업로드된 2D HTML에는 **이미** 다음 함수/구조가 존재한다.

| 원본 요소 | 확인 내용 | 3D와의 관계 |
|---|---|---|
| `#medicOverlay`·`.med-body-v2` | 3열 오버레이: 신체/상처·vitals/처치 버튼 | 화면 구분 방식은 참고 가능. 3D에 그대로 붙이면 요청한 인벤토리 소스 패널 구조와 충돌 |
| `renderMedicOverlay()` | 8부위 실루엣·상처·치료자/환자 구분 | 3D 신체 마커와 환자 선택 UX에 아이디어 재사용 |
| `woundClusters`, `treatmentClusterId` | 개별 상처와 처치 그룹의 연결 | 그룹은 표시/일괄 처리 단위. B1 `bleedSources`와 동등한 객체가 아님 |
| `getWoundClusterKey()` | 산탄은 volley+부위 기준, 비산탄은 부위+해부학적 주소 구역 기준 | 그룹을 3D 정확 좌표와 다시 맞춰야 함. 같은 구역이라는 이유만으로 같은 드레싱 면적에 있다고 단정 금지 |
| `buildClusterTreatmentPlan()` | `bandage`/`pressure_bandage` 등 그룹 적용 가능한 개별 상처 및 비용 산출 | 그룹 처치의 **eligible 상처를 먼저 확인**하는 원칙 참고 |
| `applyTreatmentToCluster()` | 원자적 자원 차감, 오류 시 복구, 개별 처치 상태 기록 | 3D의 실물 아이템 소비도 **중복 사용/부분 소모 방지**를 만족해야 함 |
| `MEDICAL_RESOURCE_DEFAULTS` | 2D에 붕대·지혈대·흉부 씰 등 **자원 개수** 기반 재고 | 새 3D 인벤토리의 개별 아이템과 **이중 재고 생성 금지**. 원본은 수정하지 않음 |

**중요:** 2D의 치료 함수/자원 수량을 3D에 그대로 이식하면 현재 B1 출혈원 적분과 동기화되지 않을 수 있다. 게임 규칙을 참고하되, 3D 수술/치료 효과는 새로 검증한다.

## 4. 3D 인벤토리: 이미 있는 것과 없는 것

### 4-1. 이미 있는 것 [코드 확인]

| 파일·함수 | 확인된 작동 |
|---|---|
| `inventory.js` / `Inventory` | 아이템 인스턴스를 `Map`에 저장. `instanceId`, `kind`, `definitionId`, `owner`, `cell` 등의 소유/배치 데이터 |
| `GRID_LAYOUTS` | `bag` 6×5, 탄약 상자(`CRATE_OWNER`) 6×6. 현재 소유자별 **고정 격자** |
| `itemSize()` | 조준경 크기 정의, 탄창 1×2, 총기 4×2, 나머지 1×1을 처리 |
| `canPlace()`·`findCell()` | 격자 범위·다른 아이템과의 충돌 판정 |
| `rootOwner()` | 총기에 종속된 탄창/부착물(`weapon:<id>`)의 실제 루트 소유자 추적 |
| `canAccess()`·`openContainer()` | 현재는 개인 `bag` 또는 접근 가능한 탄약 상자 중심 |
| `InventoryUI.down/motion/up()` | 포인터 입력으로 선택/드래그, 7px 이상 이동 시 드래그 시작, 끌고 가는 아이템 그림 표시 |
| `InventoryUI.activate/drop()/destination()` | 한번 선택 후 이동과 드래그-드롭이 공통 아이템 이동/장착 동작으로 연결 |
| `InventoryUI.toggle()` | 인벤토리 표시/닫기, 현재 접근 컨테이너와 선택 초기화 |

### 4-2. 요구사항에 비해 아직 없는 것 [소스 기준]

- `kind: medicalSupply` / `medicalKit` 같은 **의료 아이템 및 파우치 스키마**.
- 전술조끼·벨트·백팩 각각 독립된 **동적 수납 격자**. 현재 `GRID_LAYOUTS`는 `bag`과 탄약상자 중심.
- IFAK 바깥 1칸 → 내부 3×3 또는 3×4 격자 / 의료 전용 허용 조건 / 자식 물품의 무게와 수납 제한.
- 임의 수납장비를 더블 클릭·더블 터치로 여는 **이동식 비모달 창**.
- 일반 `Inventory` 하나를 넘어 **환자/다른 사람/바닥/상자** 소스를 모두 다루는 복수 소유자·접근 권한·인벤토리 패널 모델.
- 의료 물품을 상처 또는 부위에 드롭하거나 선택 후 사용하는 목적지 타입.
- UI 아이템 강조를 위한 `selectedBodyPart`, `selectedWoundId`, 적용 후보/불가 사유 파생 상태.
- 신체 실루엣 위에 **실제 3D 주소를 이용한 상처 마커와 그룹된 목록**을 동시에 표시하는 3열 정식 의료탭.

이 목록은 '전체 게임에 없다'는 보편적 주장이라기보다 **확인한 v56 모듈에서 요청한 UX가 아직 구현되지 않았다**는 의미다.

## 5. 제안 기술 경계: 엔진 로직을 UI에서 다시 만들지 말 것

```text
       [현재 3D 인체/피격·의료 상태]              [현재 인벤토리 상태]
                  │                                   │
                  ▼                                   ▼
       읽기 전용 의료 ViewModel                  읽기 전용 Grid ViewModel
       부위 8개 / 상처 ID / 마커                  소유자 / 컨테이너 / 격자
                  │                                   │
                  └─────────────┬─────────────────────┘
                                ▼
                   [공통 3열 UI + 플로팅 창]
                                │
                ┌───────────────┴─────────────────┐
                ▼                                 ▼
          아이템 이동 명령                  의료 처치 요청 명령
          (기존 inventory)               (미구현 treatment adapter)
                │                                 │
                ▼                                 ▼
          소유·격자 갱신             대상·자원·시간·효과 검증/적용
                                                  │
                                                  ▼
                                   기존 의료 출혈원/생리 엔진 갱신
```

- **[설계 제안]** 중앙/좌측 표시를 위한 `MedicalViewModel`은 **의료 스냅샷을 읽어서 가공할 뿐**, 혈액량·HP·상처 상태를 갱신하지 않는다.
- **[설계 제안]** 아이템 이동은 기존 `InventoryUI`의 포인터·드롭 경로를 재사용. 목적지만 `itemContainer` 외에 `medicalTarget`으로 확장.
- **[설계 제안]** `TreatmentAdapter`(가칭)가 적용 가능성과 지속 치료를 판단. **명칭·객체 구조는 합의 전 예시**.
- UI 강조 판단은 실제 출혈 모델의 성공 여부와 별개로, *사용 가능한 후보*만 표시. 정확한 적응증/처치 수치는 확정하지 않음.

## 6. 치료 대상의 데이터 경계: 부위·상처·출혈원은 같지 않다

| 개념 | 실제 또는 계획 필드 | 주의 |
|---|---|---|
| 신체 부위 | `m.bodyParts`, `BODY_PART_MAX_HP_S3` | 8부위 유지. 팔 한 부위를 상처 하나로 축약하지 않음 |
| 상처 | `m.wounds[]`, `w.id`, `partKey`, `bodyTrajectory.entryAddress` | 표면 마커·상처 목록의 기본 ID |
| 상처군(원본 이식) | `m.woundClusters`, `w.treatmentClusterId` | 겹치거나 인접한 상처의 관리/일괄 적용 편의; 실제 덮는 면적은 별도 확인 필요 |
| 출혈원 | `m.bleedSources[]`, `w.bleedSourceIds`, `s.woundIds` | 하나의 혈관/장기가 여러 상처에 연결될 수 있음 |
| 출혈원 병변 | `s.lesions[]` | 같은 이름의 장기/혈관 출혈을 상처마다 중복 생성하지 않음 |
| 환자(대상) | 3D `actor`/`medical` | 어느 사람의 의학적 상태인지 항상 명시 |
| 아이템 소유자 | `owner` 및 실제 환자/플레이어/컨테이너 인스턴스 | **치료자와 환자 인벤토리 독립 관리 필요** |

**특수 사례**: 관통탄 한 발에서 피부 진입점/출구점이 따로 생기더라도 내부 피격 이벤트/실제 출혈원과 1:1이라고 가정하지 말 것. 사용자에게 보이는 피부 표식과 `w.id`의 관계를 명시적 데이터로 설계한 뒤 구현한다.

## 7. 의료 물품 적용 범위 (설계 방향, 효과 수치 미확정)

| 분류 | 예시 | 화면 입력 단위 | 엔진 효과와의 관계 |
|---|---|---|---|
| 상처 국소 | 일반/압박붕대, 지혈거즈, 스펀지형 지혈장비 | `woundId` 또는 적격 상처군 | 해당 국소 출혈원/상처 상태만 취급 |
| 사지·영역 | 지혈대, 부목, 일부 접합부 압박 장비 | 부위 + **해부학적 적용 위치** | 적용 위치보다 원위부인 혈류 등. 전체 부위의 모든 내부 출혈을 자동으로 0으로 만들지 않음 |
| 체강 관련 | 흉부 씰, 바늘 감압, 복부 지혈 폼 등 | 외부 적용 위치 + 특정 상태 | 공기 유입/압력/출혈원을 각각 따로 제어. 흉강 혈흉은 완전 치료 불가 |
| 전신 | 진통제, TXA 등 | 환자 ID | 약물별 전체 상태/시간적 효과, 임의의 조직 HP 복원 금지 |

- 사용자 언급 후보: `지혈대`, `3면 밀폐 드레싱`, `흉부 씰`, `바늘 감압`, `복부 지혈 폼`, `AAJT`, `TXA`.
- **[보호 불변]** 조직 손상과 출혈에 대한 기존 계산을 치료 UI 편의 때문에 뭉개지 않음.
- **[미정]** 모든 의료 물품의 정확한 적용 위치·시간·실패/부작용·효과 강도·보유 개수·임상 근거/게임 허용 여부.
- **[주의]** 3면 밀폐 드레싱, 복부 폼 등의 의료 현실성은 별도 출처 확인 후 분류. 이 참고서 자체는 의료 지침이 아님.

## 8. 파우치/IFAK 내부 수납: 구조 확장 시 점검할 계약

### 현재 소유 표현

```js
// 실제 소스에서 쓰는 예시 필드(간략화)
{ instanceId: 'mag-02', kind: 'magazine', owner: 'bag', cell: {x:1,y:2} }
{ instanceId: 'mag-01', kind: 'magazine', owner: 'weapon:weapon-01' }
{ instanceId: 'weapon-01', kind: 'weapon', owner: 'equipment:primary' }
```

### 확장해야 할 조건 [설계 제안]

1. 아이템은 항상 **정확히 한 소유자/컨테이너**만 갖게 유지.
2. 컨테이너 아이템은 바깥 `cell`과 별도로 내부 격자 크기·적재 제한·허용 아이템 태그를 가짐.
3. **수납 아이템 안에 다시 수납 아이템을 넣는 행위**는 IFAK에는 금지. 다른 컨테이너의 중첩 허용 여부는 추후 결정.
4. 컨테이너 내부 아이템의 **실제 질량 총합 반영**. 바깥 1칸이 내용물 질량을 삭제하지 않음.
5. 접근 가능 여부(`canAccess`)를 **플레이어·환자·컨테이너·거리/상태**와 연결할 준비가 필요.
6. 재귀 루트 소유 추적을 추가할 경우 **순환 소유·자기 자신 안에 넣기·사라진 부모 참조**를 차단.
7. 팝업은 view일 뿐이고 내부 아이템 이동이 되면 원본 `Inventory.items` 상태만 갱신.
8. UI의 창 위치/열림 상태는 게임 아이템의 실제 소유/위치 정보와 분리.

**여기에는 특정 새 클래스나 JSON 필드 이름을 강제하지 않음.** `owner='container:itemId'` 같은 문자열은 설계할 수 있지만 기존 `rootOwner()`는 `weapon:` 경로만 이해하므로, 아무 검증 없이 새 문자열 규칙만 도입하면 오류가 난다.

## 9. '사용' 동작: 단일 처리 경로와 거래 원자성

```text
[아이템 드래그] ─────┐
                    ├→ identifyItem + identifyPatient + identifyTarget
[아이템 선택 후 터치] ┘                  │
                                        ▼
                         applicability + access + stock 검사
                                        │
                         [사용 중/시간 경과/취소 정책]
                                        │
                                        ▼
                         아이템 소비/처치 결과 단일 확정
                                        │
                                        ▼
                          의료 엔진에 지속 효과 연결
```

**[설계 제안]** `target` 타입은 `wound`, `anatomicalRegion`, `physiologicalCondition`, `wholePatient` 정도의 개념으로 구분할 수 있다. 이 명칭은 구현 전 사용자·작업 AI와 협의.

반드시 피해야 할 버그:
- 선택 처리와 드래그 처리의 결과가 다름.
- 같은 의료템을 빠르게 연타해 두 번 사용하거나 아이템이 복제됨.
- 환자의 상처를 치료하면서 엉뚱한 사람의 출혈원을 줄임.
- 드래그 실패/거부인데 물품만 소비됨.
- 두 개의 상처 UI가 같은 출혈원 효과를 중복 계산함.
- 처치 상태는 유지되는데 B1 `controlFactor=1` 초기화 때문에 효과는 사라짐.
- 지혈 후 장기·근육·골격 HP까지 자동으로 복구됨.

## 10. 기능 분할 제안 — 아직 패치 지시가 아님

| 논리적 층 | 목적 | 구현 완료 판정의 예시 |
|---|---|---|

**우선순위:** 사용자는 먼저 UI와 인벤토리 구조를 논의 중이다. 이 문서는 새로운 치료 수치 확정이나 의료 코어 리팩터링을 즉시 명령하지 않는다.

## 11. 검증·회귀 시 반드시 비교할 것

### 새 UI 기능 자체
- PC 1280×720, 갤럭시 S24 Ultra 가로 검사 기준 844×390에서 **3열 유지** 및 터치 드롭 정확도.

### 기존 3D 의료/전투 회귀
- **기존 총기·탄창·조준경 인벤토리 기능과 사격·장전** 변화 없음.
- 변경하지 않은 건강/정지 600틱 결과, 기존 동일 피격에서 상처 수·HP·혈액량·의식·관류/시야 출력 보존.
- 기존 B1 직접 혈관 출혈, 공동만 받은 혈관의 타박 기록, 실질 장기 출혈, 혈흉 구분 보존.
- 기존 검증 보고의 389 tests는 **기준 참고**; 새 기능 검증 결과로 재사용하지 않음.
- 원본 2D 파일 바이트/SHA 절대 불변. 3D 수정만 3D 브랜치에서 수행.
- 성능과 오프라인 실행, JS 콘솔 에러 0, 실제 모바일 수동 검수는 별도.

## 12. 아직 사용자에게 결정받지 않은 사항 (작업 AI 임의 확정 금지)

- IFAK 3×3 / 3×4의 정확한 격자, 여러 종류의 파우치/백팩 용량, 물품별 칸 크기.
- 일반 의료 UI가 검사 장비 없이 보여주는 심박·혈압·ECG·내부 장기 손상 정보의 수준.
- 의료탭을 열어두면 게임 시간/AI/출혈이 계속 진행되는지와 처치 도중 입력 제한.
- 타인 인벤토리 접근 허용/거리/장비 분리·파밍 정책.
- 다중 상처 클러스터가 실제로 하나의 드레싱으로 덮이는 공간적 기준.
- 각 치료 품목의 효과·시간·실패/부작용 수치, 의학적 출처와 게임 허용 분류.
- 플로팅 창의 다중 동시 열림·위치 저장·포커스·겹침 우선순위.
- 단축키의 키 번호·슬롯 개수·수납 우선순위.

## 13. 실무 인계 메모

1. **UX 의도는 A 문서가 기준**. B의 예시 코드·상태 명칭은 현황 설명/설계 제안이지 사용자 승인 API 계약이 아님.
2. 개발 전에 실제 `v56` 런타임과 파일 경로가 현재 브랜치에 그대로 있는지 비교.
3. 원본 2D는 비교 자료이고 코드를 **고치지 않음**. 3D 변경이 2D에 의미 있어 보이면 역이식 후보만 별도로 기록.
4. 출처 근거 수치/2D 원본 값/튜닝/사용자 설계값/게임 허용을 혼동하지 않음.
5. 검수 담당과 사용자 대화에서 **지시서 작성·코드 수정 요청이 오기 전에는 문서 보완 논의만** 진행.
6. 후속 구현 단계에서 필요한 최소 변경을 우선하고, 이미 존재하는 탄도·골격·혈관·의식·시야 계산은 보존.
