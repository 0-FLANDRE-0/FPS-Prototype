# 첫 레이드 프로토타입 개발 계획

첫 완료 목표는 단층 3D 맵에서 혼자 진입해 NPC와 교전하고, 상처를 치료하고, 물품을 회수해 탈출한 뒤 stash에 결과가 반영되는 플레이 가능한 레이드다. 기존 계산 추출을 먼저 검증하고, 3D 전투 접촉과 레이드 규칙을 각각 연결한다. 기존 CQB_Tactical.html의 계산 수치와 실행 경로는 회귀 기준으로 보존한다.

[구조 감사](structure-audit.md)와 [전환 아키텍처](3d-extraction-architecture.md)를 전제로 한다. 사용자 요구에 따라 **모바일 가로화면**을 주 플랫폼으로 한다. 시스템별 JS 분리·단일 HTML 빌드·원본 비교 검증에 이어, 첨부 M4A1 모델을 쓰는 첫 카메라·조작 훈련장을 구현했다. 아래 Core 분리와 3D 레이드는 후속 계획이다. 실행과 검증 결과는 [개발 안내](development-guide.md)와 [훈련장 안내](../apps/training/README.md)를 참조한다.

맵 규모·탈출 시간·의식상실 유예는 첫 플레이를 위한 제안값이다. 데이터와 계산의 밸런스 변경은 연결 성공 후 별도 검토한다. baseline CQB 맵을 자동으로 입체화하면 기존 교전 시선 문제가 그대로 드러날 수 있으므로, 작은 새 레이드 맵을 만들고 원본 맵은 parity fixture로 남긴다.

제외 범위는 multiplayer, 복층·계단, 총알 낙하·비행시간, 연막·섬광·수류탄, 거치·총기 개조 UI, prone의 완전한 조작·애니메이션, ragdoll, 상점·보험·제작·퀘스트·은신처, 중도 레이드 저장이다. NPC 행동이나 의료 코어에 해당 기능이 남아 있어도 첫 레이드 콘텐츠에서는 비활성으로 명시한다. 기본 격자 인벤토리는 사용자 요청에 따라 훈련장에 먼저 구현했다.

## 개발 순서와 통과 기준

### 훈련장 확장 1~3단계 — 구현

1. 원본 전체 레지스트리·최종 보조 테이블을 별도 훈련장에 생성·내장한다. 원본 114종 탄약·17종 총기와 방호구·부품 데이터를 보존하며 M4 호환 12종을 사용한다. 원본 초기화와 데이터 동등성을 비교한다.
2. 낱발 탄약·탄창·총기를 독립 instance로 구현한다. 총기 장착 슬롯·탄창 슬롯·약실·가방 소유권, timed packing/unpacking, 혼합 탄창, 탄창 교체·탈착·약실 공급·취소를 연결한다. 약실 유지와 빈 약실 재장전은 모션·시간·최종 30+1/29+1 상태가 다르다. 가방은 세계 시간을 멈추지 않는다.
3. 실제 약실 탄의 질량·총열별 탄속과 총기 질량을 읽어 운동량 반동을 계산한다. 후퇴·회전·반응 지연·부분 안정화·잔류 오차·수동 보정을 분리하며 연사 누적과 입력 우선권을 검증한다. 가스·관성·지지 값은 추정 튜닝값이다.

훈련장 후속 확장으로 6×5 가방과 6×4 월드 탄약상자, 1칸/최대 60발 탄약·세로 2칸 탄창·수납 4×2칸 총을 구현했다. 거리·LOS 검사 뒤 플레이어 왼쪽/상자 오른쪽 파밍 UI를 열고 양방향 이동·스택 병합·삽탄·탄창 장착을 같은 터치/마우스 경로로 처리한다. 장전 공간 예약과 취소의 탄약 보존을 검증한다. PC는 Tab 인벤토리·좌클릭 사격/드래그·장착 총 우클릭 메뉴를 사용한다. 단발은 강하게 복귀하고 연사도 사격 종료 후 잔류 상승을 더 줄인다.

다음은 이 발사 사건과 3D 접촉을 기존 관통·방호·상처 계산에 연결하는 전투 시험장이다. 인벤토리 중량 제한·사망 NPC 루팅·프로필 저장·레이드 정산과 다른 총기의 3D 모델은 이후 단계다. 상세 상태 계약과 조작은 [훈련장 안내](../apps/training/README.md)에 기록했다. 아래 세 실행본과 M0~M6는 전체 레이드의 별도 마일스톤이다.

기존 30~46인일 추정은 숙련 개발자 1명의 집중 작업을 가정한 초기 범위다. 추가된 독립 조준·카메라 관성·사격 감각의 조정 비용은 아직 반영하지 않았으므로 현재 확정 일정으로 사용하지 않는다. 작은 모바일 훈련장에서 조작·성능과 계산 추출 난이도를 확인한 뒤 재산정한다. 에셋 제작과 완성품 수준의 애니메이션은 별도다.

## 단계별 작업

### M0 기준 동작 확보

기준 커밋 cef2ff0을 읽기 전용 회귀 checkout으로 준비한다. 새 구현 branch를 별도로 만들고 앱은 원본과 다른 폴더에 둔다. 실행할 스위트는 감사 문서의 목록을 따른다.

정본 registry 초기화, terminalProfile 주입, builder 생성 순서를 기록한다. ON/OFF 스위치별 기본 상태와 실제 소비자를 조사하고 AI 하네스의 강제 OFF 동작도 기록한다. warning은 기준 목록으로 저장한다.

기존 seeded sandbox로 다음 대표 사례의 입력과 결과를 저장한다: 비방호 피격, hard stop, hard→soft backer, 플레이트 반복 피격, 좌우 사지, 급성 knockdown, 출혈 진행, 처치 전후, 잔여 탄 continuation. 전체 전투의 생존율만으로 계산 보존을 평가하지 않는다.

Three.js·Rapier spike에서는 모바일 WebGL2·WASM init, 내장 바이너리 로딩, 캐릭터 이동 결과 적용과 최신 scene query를 확인한다. 초기화 실패·앱 전환·회전과 viewport 변화도 다룬다. 외부 asset을 추가할 경우 출처·라이선스를 manifest로 남긴다. 단일 HTML을 실제로 파일에서 열고 HTTP에서 열어 저장 origin과 IndexedDB 지원 차이를 확인한다.

### M1 계산 경계 추출

registry와 builder를 첫 단위로 가져오고 원본 결과와 대조한다. 의료 actor state factory는 makeUnit에서 필요한 초기값을 명시적으로 구성하되 테스트용 불완전 mock actor를 제품 코드에 사용하지 않는다.

RuntimeContext는 simulation time, RNG, actor lookup, map/query port, event sink를 제공한다. 전역 GAME·UNITS·MAP_DATA 접근을 경계 밖으로 옮기고 log의 DOM 호출을 사건 소비자로 분리한다. registry 수치와 함수의 계산 순서는 변경하지 않는다.

field owner 목록에는 medical.wounds·bodyParts·legacy alias, ammo·reload, acute timer, 치료·약물, armor owner·slot·localZones가 들어가야 한다. 특히 updateUnit에서 소유하던 치료와 knockdown timer를 빠뜨리지 않는다.

부위 추첨을 담당하는 legacy wrapper와 주소가 주어진 계산을 분리한다. 기존 forced 훅으로 fixture를 만들 수 있으나, 새 contact 경로가 추첨을 거쳐 RNG를 소비하지 않게 한다. 이 변화는 순수 추출 parity와 구분한다.

### M2 3D 이동 기반

단층 map definition 한 개로 mesh·cuboid collider·navigation footprint를 생성한다. 플레이어와 NPC는 같은 Movement port를 사용한다. root·eye·muzzle offset, stance별 높이, 천장에 막힌 기립을 검증한다.

왼쪽 이동 패드와 오른쪽 시점 드래그·사격 버튼을 독립 pointer로 처리하고 이동 위치는 물리 결과를 따른다. pointer cancel·capture 상실·앱 전환·세로 회전은 held state를 초기화한다. Pause에서는 accumulator도 비운다. safe area와 주소창 크기 변화에서도 버튼을 누를 수 있어야 한다. Pointer Lock은 데스크톱 디버그 보조다. 문은 action 완료 tick에 표시와 collider가 함께 전환되는 최소 구현으로 시작한다.

단순 총 모형을 초기에 추가해 free aim과 회전 관성, 몸통 부착 카메라의 보행 움직임, ADS로 총을 들어 올리는 전환을 확인한다. 사격 버튼에서 누른 채 드래그해 조준할 수 있게 하여 두 엄지 조작을 검증한다. 카메라 흔들림과 실제 무기 방향은 분리하고 감소 옵션은 화면 연출에만 적용한다. 세부 계약은 [독립 조준 설계](3d-extraction-architecture.md#몸에-부착한-카메라와-독립-조준)를 따른다.

충돌 capsule과 탄도용 신체 구역 collider의 query mask를 분리한다. 물리 디버그 뷰에서 눈 위치·총구·신체 구역·map origin을 확인할 수 있게 한다.

### M3 전투와 의료 연결

방향 기반 ShotCommand를 먼저 만든다. target이 없는 벽·허공 사격에서도 발사 조건·ammo·총성·반동이 동일하게 적용되어야 한다. NPC target 선택과 무기 발사를 분리한다.

플레이어의 기본 탄도는 카메라 중앙 ray로 수렴시키지 않고 발사 tick의 논리 총구 위치·방향에서 시작한다. weapon pose와 기존 산포를 한 번 조합하고, 발사 pose와 shotId를 효과에도 전달한다. 무기 반동·카메라 충격은 별도로 표시하며 피격 먼지·불꽃·자국은 실제 접촉 자료를 소비한다. 섬광·탄피는 짧은 수명·개수 상한을 두고 모바일 비용을 계측한다.

wall·cover의 entry/exit pathLength와 incoming normal을 구한 뒤 기존 장벽 계산을 연결한다. 기존 잔여 위협·segment·continuation budget을 보존한다. impact velocity의 거리 retention과 barrier 손실을 중복 적용하지 않는 fixture를 만든다.

3D body proxy 접촉에서 주소를 확정하고, 방호·상처·AAR에 동일 주소를 전달한다. 첫 HUD는 출혈과 심각한 상태·처치 진행을 보여 준다. 상세 장기 진단이나 의료 내부 구조 전체를 화면에 노출하지 않는다.

### M4 PvE 연결

한 NPC의 시야→기억→utility→intent→이동·사격을 먼저 연결한다. 기존 XY 기억을 XZ 바닥면으로 투영하고 실제 eye/body sample로 수직 LOS를 검증한다.

known world와 actual world를 구분한다. AI가 관측하지 않은 플레이어 좌표를 movement goal로 받지 않는지 trace로 확인한다. 문·엄폐·벽 접촉은 observation으로 기억을 갱신한다. 반복 충돌 시 재계획·쿨다운을 적용한다.

전투가 없는 상황의 이동 동기는 기존 idle scan·room 행동으로 먼저 평가한다. 필요하면 authored patrol intent를 추가하되 현재 본편에 이미 patrol이 있다고 가정하지 않는다. 첫 단계에서는 팀 엄호·수류탄 등 선택 후보를 명시적으로 제한하고 제한 사유를 trace에 남긴다.

### M5 레이드 완주

일반 item inventory를 기존 weapon/ammo/armor/medical 자원과 연결한다. 죽은 NPC는 자기 소유 instance를 루트 container로 한 번 이동시킨다. 같은 item이 NPC와 player 양쪽에 남지 않게 한다.

루팅과 의료 UI가 떠 있어도 Active 레이드는 진행한다. Pause는 별도 상태다. Interaction port가 거리·LOS·상태를 검증하고 UI가 임의 targetId를 골라 바로 획득할 수 없게 한다.

탈출은 매 tick 조건 검사와 countdown으로 구현한다. 적 전멸·부분 탈출·유예 의식상실·동시 사망 조건을 별도로 다룬다. 결과 화면은 success·failure·abandoned와 회수·손실 물품을 보여 준다.

IndexedDB transaction으로 stash→escrow→정산을 연결한다. 완료 직전 새로고침, 저장 오류, 결과 다시 열기에도 중복 보상이 없어야 한다. mid-raid 재개는 없으며 남은 escrow는 다음 로드에서 abandoned로 정산한다.

### M6 검증과 조정

기준 장비·seed·스위치·맵 revision을 기록하고 모바일에서 2~4 NPC 레이드를 반복한다. correctness 통과 후 AI ray·path 요청과 렌더 해상도를 프로파일링한다. 필요할 때만 sense cadence·cache·render 품질을 조정하고 계산 수치 변경은 별도 PR로 남긴다. 내장 HTML의 오프라인 실행·로딩 시간·초기 메모리를 함께 검증한다.

고품질 asset을 넣기 전 greybox에서 완료 기준을 통과한다. 환경 mesh나 postprocessing으로 필요한 물리·시야·gameplay trace를 가리지 않는다.

## 성능 목표와 검증 장비

첫 성능 목표는 기준 Android·iPhone에서 가로화면, 제한한 렌더 해상도, 2~4 NPC greybox의 안정적인 30fps다. simulation은 60Hz를 먼저 검증하고 60fps 렌더는 여유가 있을 때 제공한다. 아직 측정된 결과가 아니다. M0에서 실제 기종·OS·브라우저·DPR·렌더 scale·전원 상태를 기록하고 M6에서 프레임 p95·simulation tick p95·AI 질의 수·메모리와 10분 이후 발열·성능 저하를 남긴다. 현재 844×390·640×360 터치 에뮬레이션은 2D 회귀와 별도 3D 훈련장 기능 검증이다. 소프트웨어 WebGL 환경의 통과는 실기기 3D 성능 증거가 아니다.

simulation tick p95 4ms를 초기 예산으로 제안하되 실측 후 확정한다. FPS 평균만 높고 최대 지연에서 입력이 멈추는 상태는 통과로 보지 않는다. headless 계산과 렌더 비용을 나누어 계측한다. 성능이 부족하면 NPC 수·감각 주기·shader 비용을 조정하고 worker나 navmesh는 병목의 근거가 있을 때 도입한다.

## 착수 전 결정 사항

첫 구현은 위 기본값으로 진행할 수 있다. M0에서 기준 테스트·브라우저 장비와 패키지 버전을 확정하고, M1에서 실제 추출 비용으로 일정을 다시 산정한다. 사용자 선호로 바뀔 수 있는 항목은 단층 맵의 크기, 탈출 시간, downed 조작 표현, refresh 시 abandoned 정책이다. 이 값들은 계산 core와 분리한 RaidConfig·presentation 설정으로 관리한다.
